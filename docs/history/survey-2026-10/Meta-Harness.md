# Meta-Harness deep-read (stanford-iris-lab/meta-harness) for reharness

Sources read: repo at commit 8123cca (cloned to scratchpad), paper arXiv:2603.28052 (HTML + PDF text), project page, GitHub issues, Harbor's Terminus2 source, the TB2 artifact repo, and two downstream papers. Repo: https://github.com/stanford-iris-lab/meta-harness. Paper: https://arxiv.org/abs/2603.28052. Project page: https://yoonholee.com/meta-harness/.

## (1) What it modifies

- The "harness": a single-file Python program around a frozen base model that controls "what to store, retrieve, and show while the model works" (README). Paper §3: "each harness is a single-file Python program that modifies task-specific prompting, retrieval, memory, and orchestration logic"; "The base model M ... is always frozen" (https://arxiv.org/html/2603.28052v1).
- TB2 track: the whole agent scaffold. The proposer skill says "The search space is arbitrary Python code. You can override any method, call any library, make raw API calls, add new tools, change how the LLM is called, rewrite command execution, intercept and transform observations"; the only constraint is subclassing Harbor's `Terminus2` and naming the class `AgentHarness` (https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/.claude/skills/meta-harness-terminal-bench-2/SKILL.md). It may also add a new prompt template file under `prompt-templates/`.
- Text-classification track: a `MemorySystem` subclass with `predict`, `learn_from_batch`, `get_state`, `set_state` (https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/text_classification/memory_system.py).
- Not modified: model weights, evaluation code, `meta_harness.py`, `claude_wrapper.py`, existing agent files ("CANNOT: modify any existing agent file, meta_harness.py, or claude_wrapper.py" in SKILL.md). Enforcement of this is by instruction only; see (9) and traps.
- The improver (proposer) is not modified: it is Claude Code with a fixed skill text (see (5)).

## (2) Improvement loop

- Algorithm 1 (paper §3): initialize population H of valid harnesses, evaluate each on tasks X, store (code, scores, traces) in filesystem D; for t = 1..N: proposer P queries D, proposes k harnesses, each that "passes interface validation" is evaluated and stored; return the Pareto frontier of D.
- Proposer: Claude Code with Opus 4.6, invoked once per iteration as `claude --dangerously-skip-permissions -p <prompt>` with `--model opus`, `--effort max`, tools Read/Glob/Grep/Agent/Write/Edit/Bash, a per-domain skill directory, and the API key stripped so the CLI uses subscription auth (`propose_claude` in https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/meta_harness.py; wrapper flags in `claude_wrapper.py`).
- Candidates per iteration: text-class paper run 2/iteration × 20 iterations = 40 (paper §4.1), though the shipped skill demands "exactly 3 candidates per iteration"; TB2 paper run 10 iterations × 2 candidates × 89 tasks × 2 trials (maintainer in issue #10, https://github.com/stanford-iris-lab/meta-harness/issues/10), though the shipped TB2 skill says "You MUST produce 1 new agent variant every iteration"; math 40 iterations → 109 candidates (paper §4.2). "a typical run evaluates roughly 60 harnesses over 20 iterations" (paper §3).
- Archive: plain filesystem. Per candidate: source file in `agents/<name>.py`, Harbor job dir with per-trial `result.json` and trajectories under `jobs/`, a row in `evolution_summary.jsonl` (iteration, agent, hypothesis, changes, avg_pass_rate, per_task, delta vs frontier, rollout_metrics: cost, tokens, turns), and `frontier_val.json` (best agent per task plus `_best` overall; text-class keeps a `_pareto` list). Population with Pareto frontier but "imposes no parent-selection rule: the proposer is free to inspect any prior harness" (paper §3); in practice it copies a prior agent file as the starting point (SKILL.md "copy over one of the agents in agents/").

## (3) Evaluation and selection

- TB2: every valid candidate is run on all 89 tasks × 2 trials at temperature 0.7, concurrency 50 (`run_eval.sh`; https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/README.md). Score = flat total_passes/total_trials; a trial with any error, missing result, or timeout counts as 0 (`parse_job_results`, `compute_pass_rates`). Frontier updates on a strict `avg > current_best_avg` with no threshold, no interval, no regression gate; per-task deltas are only printed (`update_frontier`). Optional `--full-eval` reruns only the frontier winner at 5 trials. Paper leaderboard numbers come from the official TB2 leaderboard protocol; the artifact README states 5 trials each (https://github.com/stanford-iris-lab/meta-harness-tbench2-artifact).
- Text-class: validation split per dataset (num_val 50, USPTO 30), offline 1 epoch over num_train (200, USPTO 50), temperature 0.0, single seed 42; avg val accuracy across 3 datasets, Pareto on (accuracy, context tokens) (`config.yaml`). Test (num_test 100/212/100) is run once via `--test`, which writes `finalized.json` and blocks further evolution under that run name (`finalize_run`).
- Math: 250-problem search set, selection "solely based on search-set performance using GPT-OSS-20B", test on 200 IMO-level problems, 3 samples per problem, 5 models (paper §4.2).
- No statistical threshold, confidence interval, or multi-seed appears anywhere in the paper or code; "Select the final candidate before viewing test results" is the only selection rule (ONBOARDING.md).
- Unverified inference: Appendix A.2 quotes a "64.4% Terminus-KIRA baseline" in the 10-iteration Opus run while the leaderboard baseline is 74.7%; the gap is consistent with the 2-trial search config and the README's warning that "many failures at higher concurrency are timeout failures", but the paper does not reconcile the two.

## (4) Leakage controls

- Text-class and math: "The proposer never sees test-set results; its only feedback comes from the search set" (paper §3). Test results live in a separate `results/` dir "never exposed during evolution" (SKILL.md), and `HeldOutIsolationTests` check that default evolution never runs test. But the README says the test data is in the public repo, so "this is operational isolation, not access control" (https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/text_classification/README.md).
- TB2: no held-out tasks. "we perform search and final evaluation on the same 89-task benchmark. We use this benchmark as a discovery problem" (paper §4.3); maintainer confirms in issue #1 (https://github.com/stanford-iris-lab/meta-harness/issues/1). The proposer reads the full trajectories of the very tasks it is scored on. Mitigations: skill rules ("Never mention task names in agent code, prompts, or comments"), plus "manual inspection and regex-based audits for task-specific string leakage" (paper §4.3). The demo's 19-task "hard" subset list is unpublished (issue #16 open).
- The experimental Harbor pilot adds a mechanical control: each task's `task.toml` declares `forbidden_references` (task name, input/output filenames) plus a universal denylist (`/tests`, `verifier`, `/solution`, `task.toml`, `test_outputs`); `controller.validate_source` rejects any candidate whose source contains them before scoring (https://github.com/stanford-iris-lab/meta-harness/blob/main/experimental/harbor_meta_harness/controller.py).

## (5) Is the improver improved?

No. The proposer is a fixed Claude Code + fixed skill; nothing proposes or validates changes to the skill, the proposer prompt, or the loop. The paper's position is that the method "can improve automatically as coding agents become more capable" (§3), i.e., meta-level improvement is outsourced to model upgrades. The skill is tuned by humans: "iterating on the skill text had a larger effect on search quality than changing iteration count or population size. Expect to run a few short evolution runs (3–5 iterations each) specifically to debug and refine the skill" (Appendix D). The only self-authored meta-material is the text-class skill's Step 0, where the proposer writes a ≤30-line post-eval report per past iteration into `reports/` for later iterations to read; these are never validated. Nothing resembling reharness's R0-vs-R1 comparison exists.

## (6) Reported results

- Text classification (GPT-OSS-120B, 3 datasets): Meta-Harness 48.6 avg test accuracy at 11.4K context tokens vs ACE 40.9 at 50.8K, MCE 40.0 at 28.5K, few-shot(all) 40.8, zero-shot 27.4 (paper Table 2). OOD on 9 unseen datasets: 73.1 vs ACE 70.2 (Table 5). Vs other optimizers on the search set (median/best): GEPA 32.6/40.2, Best-of-N 34.0/44.2, OpenEvolve 39.1/43.3, TTT-Discover 34.1/45.6, Meta-Harness 50.0/56.7 (Table 4). Interface ablation: scores-only 34.6/41.3, scores+LLM-summary 34.9/38.7, full traces 50.0/56.7 (Table 3).
- Math retrieval: 200 IMO-level problems, 3 samples each, 5 held-out models: +4.7 avg over no retriever (34.1 → 38.8), +1.3 over BM25 (Table 6).
- TB2 (89 tasks): Opus 4.6 76.4 vs Terminus-KIRA 74.7 (#2; ForgeCode 81.8 "we were unable to reproduce"); Haiku 4.5 37.6 vs Goose 35.5, Terminus-KIRA 33.7 (Table 7). The discovered change gains on 7 of 89 tasks (Appendix B.3). Whether Haiku's harness came from a separate search run is not stated in what I read: unverified.
- Compute: TB2 default search "takes about 4-6 hours and costs roughly $500 per iteration" at 89×2 and concurrency 50 (TB2 README); proposer reads a median 82 files per iteration (Table 8); "up to 10,000,000 tokens of diagnostic information" available per step (Table 1). No total-dollar figure for any paper run. Temperature/reasoning effort for the paper's Opus/Haiku runs is asked in issue #6 and unanswered; the code uses temperature 0.7.

## (7) Failure modes they report

- Six consecutive regressions in TB2 iterations 1–6: structural fixes bundled with prompt rewrites (-5.6pp, -6.7pp), confound isolated at iteration 3 (-1.1pp), further completion-flow and prompt edits regressed, a "smart-waiting" optimization regressed; the winner (iteration 7) was "purely additive" (Appendix A.2). Iteration 9's candidate "crashed before evaluation".
- Overfitting acknowledged for TB2 (same-set search) with only inspection/regex audits; the paper's own framing of code-space overfitting is "brittle if-chains or hard-coded class mappings" (§5).
- Skill-documented failure modes: "The most common failure mode is creating systems that are just parameter variants"; "Candidates that skip prototyping tend to have bugs"; delegating to subagents loses constraints (text-class SKILL.md).
- Infra noise: "many apparent failures at higher concurrency are actually timeout failures rather than reasoning failures" (SETUP.md); timeouts score 0 and feed the frontier.
- Duplicate candidate names silently overwrote landed files until PR #15 (https://github.com/stanford-iris-lab/meta-harness/issues/15).
- Reward hacking is not discussed in the paper. Downstream: RRSI reports Meta-Harness-style evolution tends to "overfit by memorizing the training tasks, showing large in-distribution gains that shrink or even vanish on out-of-distribution benchmarks" and adds a critic and pruner (https://arxiv.org/abs/2609.24972); "Auditing Harness Tampering in Self-Improving Agents" finds tampering "consistently occurs in real runs from different agents" and "often persists in the lineage of the best agent" (https://arxiv.org/abs/2609.00069; does not name Meta-Harness in the abstract).

## (9) Agent and harness design

Inner agent (TB2 `baseline_kira.py`, 1,185 lines; https://github.com/stanford-iris-lab/meta-harness/blob/main/reference_examples/terminal_bench_2/agents/baseline_kira.py):
- Single-agent ReAct loop, no planner/executor split. `_run_agent_loop` iterates `for episode in range(self._max_episodes)`; Harbor's Terminus2 default is 1,000,000 episodes, so the effective limits are Harbor's agent timeout and context (https://github.com/harbor-framework/harbor/blob/main/src/harbor/agents/terminus_2/terminus_2.py).
- Tool protocol: native tool calling through `litellm.acompletion` with three tools, `execute_commands`, `task_complete`, `image_read`; commands run in a tmux session with a `__CMDEND__` completion marker; observation cap 30KB (Terminus2 default 10KB). Anthropic prompt caching is injected (`anthropic_caching.py`).
- Retries: tenacity, 5 attempts, exponential 0.5–4s, excluding context-length and bad-request errors; per-call LLM timeout 900s; infrastructure calls wrapped in a 600s block timeout.
- Context management (inherited from Terminus2): proactive summarization when free tokens fall below 8,000; on `ContextLengthExceededError`, unwind messages to free 4,000 tokens, run a three-step subagent summarization (summary, gap questions, answers) and hand off; ultimate fallback is the instruction plus the last 1,000 chars of the screen.
- Stop/finish: double confirmation. First `task_complete` returns a checklist ("Does your solution meet the requirements ... account for potential changes in numeric values ... verified from the perspectives of a test engineer, a QA engineer, and the user"); a second `task_complete` ends the episode; any intermediate command resets `_pending_completion`, which the proposer diagnosed as the "verification spiral" (A.2).
- Memory: none across tasks; state resets per task (paper §2 contrasts this with continual-learning memory search). Prompt: `terminus-kira.txt` with `{instruction}` and `{terminal_state}` and a "minimal state changes" directive.

What is mutable and how a change is represented:
- Mutable surface = the single candidate file (any method override, new tools via `TOOLS` + `_parse_tool_calls`, prompt template, LLM call parameters, command execution) in TB2; the `MemorySystem` methods in text-class. Fixed = benchmark, task set, model, `meta_harness.py`, wrapper, baselines.
- Representation = a whole Python module produced by copy-then-edit, not a diff, patch, or DSL. Each candidate carries a JSON record in `pending_eval.json`: name, import_path, hypothesis ("falsifiable claim"), changes, expected_efficiency (TB2) or axis/base_system/components (text-class).
- Versioning = immutable files per candidate plus append-only `evolution_summary.jsonl`; lineage only as the `base_system` field or the proposer's prose; no git, no rollback needed since baselines are never edited and the frontier simply points at the best file.

Isolation and testing before use:
- Validation chain: subprocess import check and exact class/subclass check (`--validate-agent`), then a 1-trial smoke run on `extract-elf` requiring `n_errors == 0`, then the full evaluation. Appendix D: "A simple test script can catch most malformed or nonfunctional candidates in seconds."
- Sandboxing: task shells run in remote Harbor sandboxes (Runloop or Modal; Docker per task). The candidate agent code itself runs in the Harbor host process with the host's API keys; only its shell commands are sandboxed. The proposer runs with `--dangerously-skip-permissions`, Write/Edit/Bash, in the experiment directory; its isolation is from local Claude config (`--setting-sources ""`, empty `--plugin-dir`, `--strict-mcp-config`, `--disable-slash-commands`), and every session is logged (meta.json, events.jsonl, per-tool dumps).
- The Harbor pilot is the stricter design: candidate source is "never imported by the long-lived outer Harbor agent or controller"; `controller.py` runs as a short-lived subprocess, stages the file in a temp dir, AST-checks `class AgentHarness(BaseAgent)` with `async run`, applies the denylist, then launches a child Harbor job per task; the outer agent only has `run_command` and a bounded `evaluate_harness` tool (`eval_budget` 4–8 calls) with a frozen append-only `EvaluationState`, and the verifier returns the best reward in that history (https://github.com/stanford-iris-lab/meta-harness/blob/main/experimental/harbor_meta_harness/README.md).

## (10) Self-improvement design

- Signal: per-task pass rates and the frontier, the full execution traces of every trial under `jobs/` and `logs/`, every prior candidate's source, `evolution_summary.jsonl` rows (hypothesis, outcome, delta, cost/tokens/turns), and the proposer's own post-eval reports. The ablation (Table 3) is the paper's central claim: raw traces are "the key ingredient"; LLM summaries "do not recover the missing signal, and may even hurt".
- Diagnosis: both per trajectory and aggregate. TB2 skill Step 1: one subagent reads state files, then "Deep-read failed AND successful trajectories. Most important step", and returns STATE / HYPOTHESIS (falsifiable) / CANDIDATE with a predicted pass-rate and token impact; Step 2: a second subagent implements and smoke-tests. Text-class skill forbids subagents, requires prototyping in /tmp against real logs and a self-critique for "parameter variant" before writing the file. Rules: "One mechanism per candidate", "Mechanism-first ... Never add changes speculatively".
- Avoiding refuted ideas: no formal archive query, dedup, or novelty metric. It relies on the proposer reading `evolution_summary.jsonl` ("Check evolution_summary.jsonl for what's been tried"), skill heuristics ("If last 3 iterations explored the same axis, pick different ones"; exploitation axes A–F), and emergent causal reasoning: A.2 shows the proposer isolating a confound, concluding "modifications to prompts and completion flow are high risk", pivoting to an additive change, then composing and transferring a lesson from an earlier run. Table 8 shows it reads 69–99 files per iteration, 41% prior source and 40% traces.
- Stopping: fixed `--iterations` (default 5 TB2, 20 text-class); the skill forbids the proposer from writing "the frontier is optimal" or stopping early; SIGINT finishes the current step. The Harbor pilot stops on `eval_budget` exhaustion (a count, not money). There is no convergence test, no significance test, and no dollar budget in the reference code; costs are recorded after the fact in `rollout_metrics`.

## For reharness

- Borrow: (a) the trace-level archive. Meta-Harness's one hard result is that score summaries lose the signal (Table 3). reharness's R sees per-task failure summaries and its own notes; giving R grep/cat access to the raw trajectories and package source of every prior candidate (still train-only projection) is the cheapest likely gain. (b) Per-candidate `hypothesis` + `prediction` + `expected cost` fields in the ledger, so a rejection records what it refuted (reharness's R1 asked for exactly this). (c) The "purely additive first, control-flow and prompt rewrites are high risk" lesson and one-mechanism-per-candidate rule, which match reharness's v0.1/v0.2 pattern of accepted end-of-task checks and rejected hooks. (d) Environment bootstrapping as a concrete W idea: snapshot the SaaS state (sheets, channels, contacts) into the first prompt. (e) The Harbor pilot's per-task `forbidden_references` static denylist before any paid gate.
- reharness already does better: a sealed, pre-committed held-out final with bootstrap intervals (Meta-Harness has no interval anywhere and searches on the TB2 test set); a dollar budget ledger with reservations (Meta-Harness has iteration counts and $500/iteration); a gate with min_gain and regression tolerance (Meta-Harness promotes on any strict improvement of a 2-trial flat average, so one task flip of 0.56pp is "NEW BEST"); candidate code executed in an isolated Docker worker without framework handles (Meta-Harness's candidate agent runs in the host eval process); and an actual R0-vs-R1 protocol, which Meta-Harness has no equivalent of.
- Trap 1: "discovery problem" framing. Searching on the scored set and reading its trajectories, with regex audits as the only leakage check, is the practice RRSI later measured as gains that "shrink or even vanish" OOD. Do not import TB2-style same-set search even for a cheap inner loop.
- Trap 2: selection on noise. 2 trials × 89 tasks, single-seed 50-example validation, and strict-> frontier updates are a noise amplifier; reharness's 25-task dev gate has the same arithmetic (RESULTS.md: one task is 8 points on 12), so the Meta-Harness recipe of "more candidates per iteration" would only widen the winner's-curse unless attempts per gate rise first.
- Trap 3: unenforced boundaries and unvalidated self-memory. The proposer runs with `--dangerously-skip-permissions` and full write access; "CANNOT modify meta_harness.py" is prose, and the proposer's post-eval reports are read by later iterations without any check. reharness's fixed K and the rule that R's self-changes only count after a downstream W* comparison are the right defaults; do not loosen them to copy Meta-Harness's speed.
