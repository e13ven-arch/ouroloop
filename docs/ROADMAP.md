# ouroloop 路线图（v0.5）

> 2026-09-27。目标与协议以 [DESIGN.md](DESIGN.md) 为准；本路线图覆盖任务策略 W 与研究策略 R 的完整改进闭环。
> 实施前阅读 [架构审查](RSI_REVIEW.md)和 [模块详细设计](modules/README.md)。模块编号与本页里程碑编号不同，映射及共享文件责任见模块入口。
> **M1 运行契约已完成**（真实上游 `4a8e106` / package 1.0.6，split 已冻结）；**M3 的信号路径 1 已实现**（完成度探针）。尚无真实模型业务成绩。M2、M4～M7 未实现；当前 CLI 只开放 smoke，其余阶段均为目标接口。M1/M3 下的测量和测试数来自已有记录，本次未重跑。

## 0. 当前基础与缺口

| 已有可复用实现 | 业务主线缺口 |
|---|---|
| 决策点、runtime、账本、默认回退，业务工具与 split 契约 | 实际装配检查、统一策略描述、行为缺口与版本关联 |
| build/check、插件训练、worker、模型库与服务，完成度探针 | 真实轨迹、分组训练与有增量价值的小决策模型 |
| replay 与单候选任务评测、门、注册表与发布三元组 | 配对完整任务评测、W/R 完整版本的校验和安装 |
| 独立研究候选循环、prompt suite、世代循环 | 将诊断、候选、可选训练、任务评测和新版本采集接通 |
| 游戏与代码任务示例 | AutomationBench 的实测、领先模型比较、可复现报告 |
| 研究员提案接口和实验历史 | 研究策略 R 的版本化、比较与下一轮回用 |

已有实现是工程起点，不代表 C1～C4 已成立。C1～C3 属于任务能力证据，C4 属于研究能力证据。历史游戏结果继续留在日志，不作为业务成绩。

## 1. 完成目标与顺序

业务阶段交付：Marketing 上的任务改进、领先模型比较，以及小决策模型有无增量价值的结论。完整框架还必须交付 M7：研究方法被系统提出、验证、安装，并用于下一轮改进。分阶段可发布，不能将只完成业务循环称为全部递归能力已实现。

```text
M1 已有契约 → M2 真实基线与行为缺口 → M3 补齐真实干预证据
                                            ↓
M6 业务比较 ← M5 任务自动改进与经验继承 ← M4 策略构建与训练评测
                ↓
              M7 研究策略改进 → 新研究策略回到 M5 → 完整 RSI 报告
```

当前下一步是 M2 的真实模型基线，并补齐 M3 的真实干预证据。M1 不重做。M5 冻结研究策略，M7 再开放有限目标；二者复用同一执行管线。M6 可先发布业务结果，也可等 M7 开发完成后统一运行最终测试；已经公开的测试结果不能再作为后续调优的独立证明。

## 2. 实施工作项

### M1：接入 AutomationBench 与运行契约

**目的：** 能用同一驱动器运行目标模型和领先模型，拿到与官方语义一致的结果。

**状态：已完成。** 在真实 checkout（`zapier/AutomationBench` @ `4a8e106`、package 1.0.6、Python 3.12.14、`api` 工具集）上跑过 `--phase smoke --checks-only`，25 个 dev 任务全部通过契约检查，split 已冻结（train 52 / dev 25 / test 23 个任务，一任务一家族）。

**已改动：**

- `ouroloop/benchmark.py`：任务分组 manifest（冻结后不可改派，重复冻结同一内容不算改动）、运行 manifest、`TaskResult`、预算。两条规则写在记录里而不是交给调用方：split 按家族分配，所以同一任务的全部尝试、分支和重复都落在同一侧；`ids()` 必须指名 split，空调用报错。未测到的费用一路保持缺失，不在汇总里当成零。
- `ouroloop/adapters/automationbench.py`：延迟导入上游，缺什么就说缺什么、为了什么而缺。agent 拿到的是 `BenchTask`（prompt 与被授予的工具名）；断言和初始状态在它收不到的 `Grading` 里，评分只读工具留下的世界。只接上游默认的 `api` 工具集（`api_search`、`api_fetch`、`base64_encode`），其他工具集直接拒绝而不是悄悄替换。
- `ouroloop/evolve/task_eval.py`：一次尝试 = 新 episode + 新 agent + 官方评分；预算超出记 `budget` 终止，provider 或 harness 失败记无效尝试而不是零分。test split 的 session 标记 `held_out`，已有的建数据路径取不到它。
- `ouroloop/bench.py` 与 `cli.py`：`ouroloop bench --config ... --phase smoke [--checks-only]`。
- `examples/automationbench/marketing.toml` 与同目录 README：依赖、命令、smoke 阶段能与不能证明什么。
- `tests/fake_upstream/`：上游的微缩替身（两个任务，其中一个是"正确做法是什么都不做"的反向任务），使适配器的测试不需要真实上游。

**已验收：**

- 适配器契约检查 `contract_check`：在依赖装齐时，把官方 rubric 入口、服务订阅门（`compute_allowed_services`）和工具 schema 与上游自己的实现对比，并说明哪几项比不了；对每个被指名的任务核验快照与世界互不影响，再核验一次与断言无关的写入不会移动分数。
- 错误写入不能被文字总结变成成功：有测试写错联系人再发一条"已完成"的消息，得分只反映写错的那一半。
- 输入审计：agent 可见载荷只有 system prompt、触发消息和工具 schema；断言、期望值或初始状态出现在其中就是 leak。prompt 里合法出现的长字符串（任务本身要求写的措辞）列为待人工查看的 overlap，不判失败。
- 模拟操作不调用真实 SaaS：任务只订阅它 seed、断言或授予工具的服务，其余被上游以凭据错误拒绝；此外 episode 在工具运行期间隐藏 `OPENAI_API_KEY`，使模拟的 ChatGPT 动作走上游自带的离线分支。
- 隔离与分支：`Episode.snapshot/restore` 基于世界的深拷贝；上游 `WorldState` 是 pydantic 模型，`contract_check` 逐任务核验而不是假定。reset+前缀重放尚未需要，留到 M3 按信号路径决定。
- 382 个测试通过、1 个跳过（新增 96 个）。检查过程发现两个真实缺陷：初始状态与工具写入的世界共享嵌套结构，导致 agent 满足的断言被当成"本来就成立"而被排除出分母；leak 审计原先搜索 JSON 渲染，prompt 里粘进去的断言在那里是转义的，搜不到。

**真实上游上的核验结果（装了 `verifiers` 与 `openai-agents`，所以每一项都是真比过，不是跳过）：**

- 官方 rubric 入口就是适配器调用的那两个函数：`create_rubric()` 给出 `['partial_credit', 'task_completed_correctly']`、权重 `[1.0, 0.0]`。
- 服务订阅门与上游自己的 `compute_allowed_services` 在 25 个 dev 任务上逐个一致。
- 工具 schema 的参数名与必填项与上游自己的生成器（`agents.function_schema`）一致。
- 快照独立性在真实 pydantic `WorldState` 上逐任务核验：快照后的写入不进快照。
- 与断言无关的写入不移动分数；25 个任务 0 处 leak（26 处 overlap 都是任务本身要求写的收件人地址）。
- 家族检查：把断言的**期望值**也算进任务签名后，100 个任务里**任意两个的签名重叠都不超过 0.42**；本次冻结实验采用一任务一家族，`[bench.families]` 为空。**这只是启发式重复检查，不足以证明工作流语义独立**：不同期望值也可能来自同一流程变体。只按工具与断言类型算时有 172 对超过 0.8，同样不能直接断定是变体。后续正式泛化结论需核查家族；发现跨 split 依赖应记录局限，不能原地改已冻结结果。

**M1 的关键测量（支持干预点假设）：** dev 任务需要**中位数 12 个**计分断言（均值 14.1，最多 39）全部通过；`task_completed_correctly` 是合取，没有任务靠什么都不做就能通过。若假设 12 项独立且可靠率相同，90% / 95% / 98% 的单项可靠率分别对应约 28% / 54% / 78% 的整体通过率；这是数学示意，不是模型测量，实际要求可能相关。一次遗漏足以使任务失败，因此完成判断值得研究；真实 agent 是否主要败在这里、可见信息是否足够，仍由 M2 验证。

**尚未做（M1 剩余）：**

- 未做真实模型运行，因此没有真实的 `TaskResult`、轨迹和用量。需要凭据与预算。
- 费用未测：`cost_usd` 为 null，汇总说明缺在几次尝试上，不报成零。
- `zapier` / `limited_zapier` 工具集未接（schema 由另一个包生成）。

**入口：** `ouroloop bench --config examples/automationbench/marketing.toml --phase smoke`。

### M2：建立领先模型与目标 agent 基线

**目的：** 明确起点、成本和真实失败；避免训练一个解决次要问题的模型。

**改动：**

- 配置目标底座和至少两家供应商的领先模型；按 DESIGN §3.2 记录选择来源、准确 ID、effort 和 fallback。
- 增加 `evals/automationbench/` 的结果 manifest、任务成本与失败切片报告；大体积原始记录可使用外部版本化存储并保留摘要和校验和。
- 各模型在相同 train/dev 范围运行。冻结 test，最终评测前不查看它的运行结果。
- 优化合理的基础 prompt，形成 base 与 prompt_best；这部分支出计入搜索预算。
- 记录完整成功率、局部断言、工具用量、模型用量、延迟、无效尝试，诊断信息不足、错误目标、错误操作、过早结束等有证据的失败。

**验收：**

- 每项结果可追溯到一次具体运行，空值与缺失费用不会被当作零。
- 输出行为缺口记录（预期、实际、证据、验收），验证 `stop/on_finish` 是否是优先干预点，以及任务要求和工具执行证据是否进入可见输入；假设不成立时依据轨迹换点。
- 新建 `research/inspection.py` 的最小 runtime 快照：实际加载版本、启用点、输入字段、默认策略和动作执行者。不能只读计划文件推断当前状态。
- 如果基线尚不稳定，先修运行器；如果失败没有可学习的决策结构，记录并调整切入点。

**拟实现入口：** `ouroloop bench --config examples/automationbench/marketing.toml --phase baseline`（现在被拒绝并指向本节）。

### M3：验证一次有效干预，构造训练反馈

**目的：** 先知道选择有机会改变结果，再把它变成学习问题。

**状态：信号路径 1（局部可核验结果）已实现；干预点已按 M1 的测量选定并在离线验证过机制；尚无真实运行的收益证据。**

**已改动：**

- 当前试验接点：`stop` 的 `on_finish`——"活是不是真干完了"。M1 的断言结构提供遗漏风险的依据，M2 仍须验证真实失败分布。模型只看当时合法可见的任务与工具证据；离线标注可读隔离环境快照，两者不等价。现有 `policy.ACTING` 只允许 `stop` 执行。
- `adapters/automationbench.CompletionProbe`：每个 stop 决策处留一份世界快照，episode 结束后用官方 rubric 给每份快照打分，给当时做的决策写 `env` 标签（`yes`/`no`，附 partial_credit 与 `passed/scored`）。**离线**：评分发生在运行之后，StopGuard、view 和 agent 都看不到，官方评分器不做在线 checker（DESIGN §5.2）。训练的是完成判断，不是"继续一定有收益"。
- `agent/tools.ToolSurface.mutates`：由工具面回答"这次调用可能改了世界吗"，探针按 agent 的改动计数去快照。原先循环拿工作目录的工具名（write/edit/bash）去问，业务工具面永远答不上来。
- 只在 train split 上挂探针（`run_attempt(probe=True)` 在其他 split 上报错）；session 的 `held_out` 改为 `split != "train"`——dev 是用来裁候选的，它的标签进训练就是拿裁判数据训练。

**已验收（离线，不花 API）：**

- 同一个脚本模型、同一个任务：点不执行时任务失败（partial 0.5），且这次漏掉被记成 stop 的 `no` 标签；一个有把握的"没干完"把 agent 送回去干活，任务通过（1.0）；答案低于阈值时走默认，什么都不变。
- 每个状态由它自己的快照打分（早期状态 0.5、最终状态 1.0），不是全部用结束时的状态。
- 标签是 `env` 来源，现有 `ledger.training_rows("stop")` 能直接取。
- 快照代价：最大的真实 world 上每份 1 ms、0.1 MB，探针有 `max_snapshots` 上限。
- 过程中发现一个会毁掉全部训练数据的缺陷：`Budgeted` 包住 episode 却没有透传 `mutates`，于是改动计数一直是 0，探针把每个 stop 决策都按第一次停下时的状态打标签。现在探针构造时就拒绝"答不出改动"的工具面，而不是照样产出这种数据。

**尚未做：**

- 信号路径 2（有限分支比较）未实现。快照/恢复的机制已核验，分支后续策略、重复数与预算记账未做。
- 没有真实运行的干预收益：需要真实模型跑 train/dev，才能说这个点上的判断有没有可学的结构。
- prompt/workflow 对照（`prompt_best`）未做——DESIGN §1 要求先用 prompt 解决，小模型必须比它更好才算成立。
- `ledger.py` 的反馈关联元数据只到 point / decision / split / 任务组 / score 这一层，构造器版本号未加。

**其余改动（未做）：**

- 人或现有研究接口根据 M2 证据提出有限改动，先形成有效的 prompt/workflow 或决策干预。
- 在适配器中实现一种反馈路径：局部环境核验，或少量分支的后续结果比较。
- 扩 `ledger.py` 的关联元数据；反馈记录 point、decision、任务组、split、状态摘要、候选、后续策略、预算、重复数、证据与构造器版本。
- 同一状态分支使用可验证的环境副本；不能克隆时验证前缀重放等价。所有分支仍归原任务组。
- 标签不明确时留空；LLM 诊断不能伪装成 env 标签。确定性约束直接实现为规则。

**其余验收（未做）：**

- 展示干预前后完整任务结果的差异；事后最佳分支单独标为机会分析，不报成可部署成绩。
- 训练输入仅来自决策时可见信息；train 标签证据可逐条追溯。
- 整段失败不会自动把全部决策标错；test 任务及其变体不能进入数据生成。
- 如果干预没有收益或信号不足，输出负结论，先修改假设；不以扩大模型或增加专家数量作为默认补救。

**拟实现入口：** `ouroloop bench --config examples/automationbench/marketing.toml --phase collect`。

### M4：构建可替换策略，训练一个小模型并测完整任务

**目的：** 验证 C3 所需的增量机会；局部准确率只用于诊断。

**改动：**

- `evolve/build.py`、`checks.py`：业务任务按家族切分；train 内部验证/校准与外部 dev/test 明确分开；信号语义变更时不复用旧标签。
- `evolve/pipeline.py`：复用 train/check/store/serve，训练前固定数据和配置；一个模型或适配器，不建立专家池。
- 新建 `policies.py`：薄策略描述（owner、target、binding、输入/输出 schema、实现引用、适用性与回退）。先接现有 spec/recipe/prompt/model；规则和 workflow 仅对已注册目标开放，不开放任意仓库修改。
- 为当前宿主声明可观察、可控制、可修改与可反馈能力，按 DESIGN §5.3 映射现有接口；不为其他 harness 提前写完整集成。
- 扩已有 `evolve/task_eval.py`：候选在隔离 runtime 完整运行任务，配对汇总任务结果和成本。
- `policy.py`、`stop.py`：显式 benchmark 执行策略、默认回退与固定阈值；证明确实采用了模型动作，评分器不进入在线控制。
- `gate.py`、`release.py`、`registry.py`：task profile 与原 decision profile 分开；完整候选身份冻结、开发证据裁决后才更新版本。
- 候选先做声明、加载与机制检查，再在少量目标失败和回归任务上筛选，通过者进入固定完整 dev 评测。安装先验证整套输入规格、prompt、模型和默认策略，失败保留旧版本。

**验收：**

- 模型能加载、输出合法动作，实际行为与账本一致，服务失败走既定默认。
- 能区分提案、实际加载、触发和最终执行；未触发、触发无效和引入回归分别有记录。未触发不自动等于候选错误。
- 使用同一最终 prompt/workflow，比较默认策略与小模型，报告完整任务通过率、差值区间和全部运行开销；若最佳无模型方案 prompt_best 与此不同，也保留它，判断训练方案是否值得替代已有方案。
- 历史标签 replay 变好但完整任务变差的候选，不能凭局部指标晋升。
- 训练费用、数据生成费用均被记录；无收益时保留 prompt_best，C3 标记未证实。
- 对触及的执行、数据与版本边界运行必要回归检查，不改变旧 profile 的限制。

### M5：任务策略自动改进与经验继承

**目的：** 让改进过程可重复执行，已有 pipeline 不再只是单轮作业。

**改动：**

- 新建 `research/experiment.py`、`context.py`；扩现有 `ResearchAgent.step`、`research/loop.py`。反馈整理和策略设计是逻辑阶段，不新增独立 Analyst 服务。
- `generations.py`：检查实际装配 → 采集 → 行为诊断与经验检索 → 提案 → 准入 → 构建/可选训练 → 完整任务评测 → 安装 → 下一轮。
- `plan.py`：task profile 按总预算、可执行性、标签可用性和重复实验记录准入，不误用旧局部风险门的样本数量要求。
- `experience.py`：保存原始证据和带来源的摘要，记录行为缺口、正负尝试、机制活动、回归、适用版本及停止原因；先按标签检索，不建新记忆服务。
- 固定研究策略 R0，但为每次提案记录 R 版本和经验快照；W 更新与 E 增长各自可追溯，为 M7 留接口。
- 保留 manual provider，先验证手动提案可执行，再接 LLM；LLM 提案不直接写冠军指针。

**验收：**

- 至少两个相连的改进轮次：后续采集记录了上一轮选定版本的身份；接受、拒绝、跳过均可被追溯。
- 同一预算内可完整停止；无收益不会被强行晋升。重启复用已完成且身份一致的尝试；中断后状态不明的付费调用单独记录，重试支出计入预算。
- prompt-only 轮次不调用训练器；无标签的训练提案被拒绝并说明缺口。
- 研究员能看 train/dev 的失败，不能读 test 轨迹或断言。
- 下一轮能引用此前失败/回归证据改变提案；输入或策略版本改变时，旧经验注明适用性。仅写一段反思不算继承完成。
- 最后一轮无验证预算时不安装新策略，未评测提案单独保存。
- 多轮运行成功是工程验收，不要求每轮或最终分数预定上涨。

**拟实现入口：** `ouroloop bench --config examples/automationbench/marketing.toml --phase improve`。

### M6：独立测试、领先模型比较与可复现交付

**目的：** 给出 C1/C2/C3 的正式结论，展示改进过程和最终能力。

**改动：**

- 在查看 test 结果前冻结最终候选、所有对照、模型设置、预算、重复数、主要比较与非劣界限（若主张省钱）。
- 同条件运行领先模型和 base/prompt_best/evolved；对照身份相同则复用。
- 新建 `report.py`：成功数/任务数、区间、质量—成本图、开发迭代曲线、全量尝试状态、候选血缘与回放。
- 更新已实现命令的使用说明，发布配置、依赖锁、manifest、改动、模型卡和证据索引。

**验收：**

- 所有预定比较完整报告；基础设施无效尝试按事先规则补齐，不能挑最佳种子或删除有效失败。
- 公开自留测试与官方私有榜单分开。只在 Marketing 测试时，标题明确范围。
- C1/C2/C3 分别标记“支持／未证实／退化或仍落后”；不因最终结果不好重新选版本。
- 报告数字可从机器可读结果重算；所有费用列明实测、估算或缺失。
- 另一位开发者可按配置运行同一协议；远程模型波动通过版本、时间和重复统计说明，不承诺字节级相同输出。
- 真实模型调用、GPU 与完整复跑需要凭据和预算；离线回放只展示已有证据，不能冒充重新训练。

**拟实现入口：**

```bash
# 拟实现接口；当前版本不能直接运行。
ouroloop bench --config examples/automationbench/marketing.toml --phase evaluate
ouroloop bench --config examples/automationbench/marketing.toml --phase report
```

### M7：研究策略的递归改进

**目的：** 系统不仅更新 W，还能更新 R，并用经过验证的 R 继续改进 W。这是完整 v0.5 的正式工作项，不以额外训练一个研究员模型为前提。

**前置：** M5 能运行和记录完整改进过程；有可复现的研究缺陷，例如重复无效提案、遗漏关键输入检查或没有针对回归修改假设。没有这样的证据就继续采集，不虚构元研究目标。

**改动：**

- 将 `research.diagnose`、`research.retrieve`、`research.propose` 和 `research.preflight` 的有限 prompt/声明式配置注册为可改目标，不执行生成策略代码。先开放一个有证据的目标；不开放评分、预算上限、test 访问及正式裁决。
- `Experiment.owner = research` 与 worker 候选使用同一数据结构、版本存储和安装路径。新建 `research/campaign.py`，调用已有 M5 循环，不另建调度器。
- 从同一初始 W、经验快照、任务池和预算，运行固定 R 与候选 R' 的隔离短 campaign；各支新经验独立，评测期间研究版本冻结。所有内部训练、模型调用和评测费用归入总预算。
- 输出各支最终按开发协议选定的 W、完整任务效果与研究支出；不能把候选接受率当研究能力主指标。
- 按 DESIGN §6 划分研究开发与最终评价数据。现有业务 test 不改派、不透给内部研究；已经看过的 M6 测试不重复用于新的独立主张。

**工程验收：**

- 至少一个研究策略候选由当前研究员从实验证据提出，经过比较和固定执行器裁决。人工提供的候选只算接线验证。
- 有被接受候选时，记录 `R0 → R1 → R1 产生 W2`，下一次提案实际使用 R1；拒绝或加载失败保留 R0。验收拒绝/回退路径不能代替成功回用路径。
- 研究员无法自报得分或改晋升规则；两个 campaign 的起点相同、费用完整、经验不串用。
- 重启能恢复 W/R/E 一致版本，不能混合旧研究策略与新候选身份。

**C4 效果验收：**

- 预先锁定 R/R'、起点、任务组、预算与重复次数，比较相同研究预算下最终任务质量，或达到预设质量所需全部成本。
- 独立配对 campaign 是比较单元；多次研究同一任务不能冒充新的独立证据。初期任务量不足时只声明机制可运行、C4 未证实。
- 说明收益发生在哪种研究方法和范围。减少调用但产出更差、或者仅多看了历史，都不能算 C4 成立。
- 若已使用 M6 的 test 修改研究方向，另取未使用任务组；也可以先完成 M7 开发再统一运行锁定版本的最终测试。

命令先复用内部实验入口；确认评测契约后再设计公开 CLI，不新增当前不可运行的命令示例。

## 3. 暂缓与扩展条件

| 项目 | 条件 |
|---|---|
| 其余业务域 | Marketing 的运行、反馈与评测链条可复用；另固定任务划分，报告域内或跨域设置 |
| 第二个决策点 | 第一个点有可测价值，且基线显示新的主要瓶颈 |
| 第二个可训练专家 | 现有模型/规则不能经济地解决独立缺口，新增成本有预算 |
| 直接用终局 reward 做 RL | 局部监督不足，且有足够可复位环境与 rollout 预算 |
| 训练研究用小模型 | M7 已有证据说明某种重复判断值得学习，并有对应反馈；M7 本身无需等待训练 |
| 多层 agent、候选树和跨域策略市场 | 当前有限目标与顺序实验出现可测瓶颈，再单独论证；不作为完整 RSI 的必备模块 |
| 真实业务部署 | 另验证分布、权限、反馈时效、监控与回退；benchmark 不能替代 |
| 游戏能力扩展、实时 UI、新云调度 | 不属于本版依赖；游戏仅保留 smoke 和回归用途 |

## 4. 本次设计变更的边界

训练、模型库与服务继续复用；原部署策略不删除。任务策略和研究策略共用有限目标、候选、评测、经验与版本机制，按 M2～M7 逐步接入。

不以游戏分数、逐代单调、额外研究员模型或大规模消融矩阵作为交付前提。任务层保留小模型是否值得的必要对照，研究层只增加证明 C4 所需的同起点 campaign 比较。

本次只更新设计。M1 的运行契约与真实上游检查、M3 的完成度探针和离线干预记录保留；没有新增代码、模型运行或收益。当前待做是 M2、M3 剩余项及 M4～M7，完成状态按各节更新。
