# ouroloop 设计（v0.4）

> 2026-09-27。当前主线：在 AutomationBench 上验证基于执行反馈的 agent 改进闭环，与业界领先模型比较完整任务表现。
> 本文定义目标；代码决定实现状态。**已建**表示有对应实现，**改造**表示复用现有模块但行为需扩展，**新建**表示尚未实现。本文没有新增实测成绩。
> 实施见 [ROADMAP.md](ROADMAP.md)，研究员见 [RESEARCH_AGENT.md](RESEARCH_AGENT.md)，演示见 [DEMO.md](DEMO.md)，历史证据见 [JOURNAL.md](JOURNAL.md)。

## 0. 目标与证据现状

ouroloop 从任务执行反馈中学习可复用的小型决策策略，在有限预算下改善 agent 的完整任务表现。

首个验证环境是 **AutomationBench 的 Marketing 公开任务**。改进后的 agent 要在独立任务上，相对自己的初始版本取得收益，并与实验启动时业界领先的模型系统比较成功率、成本和延迟。小决策模型是核心研究路线；是否值得保留，由它对完整任务的增量效果决定。

闭环为：**执行业务任务 → 记录决策与结果 → 诊断可改进的失败 → 修改策略／训练小模型 → 完整任务评测 → 选定新版本 → 再执行。**

新版本在训练池继续执行，获得它实际到达的状态和反馈。所有失败与无收益实验保留。更换版本不保证下一代更强；开发集筛选也不保证独立测试收益。

已有决策点、账本、监督数据构建、训练器插件、训练作业、模型库、服务、版本与晋升机制，以及场景世代循环和独立研究候选循环。**尚无 AutomationBench 适配器、业务训练信号方案、业务任务晋升闭环和实测收益。** 研究候选循环尚未成为世代训练循环里的自动研究员。游戏实验用于检查机制，不作为业务能力证据。

## 1. 第一性原理与范围

| 原理 | 设计含义 |
|---|---|
| 任务结果是目标 | 决策准确率、Brier、训练 loss 用于诊断，交付由完整任务效果决定 |
| 训练必须带来价值 | 能用明确规则或 prompt 解决的问题先用它们；小模型需要改善质量、成本或延迟 |
| 封闭输出不代表判断简单 | System 1 是分工启发，不据此认定二分类都适合小模型；信息不足或复杂推理留给原处理方式 |
| 最终得分不等于逐步标签 | 一次失败不能把全部动作标错；训练信号要写清生成方法与局限 |
| 策略改变状态分布 | 历史记录上的拟合只能说明局部表现；候选还要真实控制任务并重新评测 |
| 简单方案先取得证据 | 先一个业务域、一个决策点、一个可训练模型；新增组件对应已观察到的问题 |
| 评价条件固定 | 改进者不能改评分器、测试池、预算、模型比较条件或晋升门 |
| 结果可重算 | 版本、任务、尝试、失败、用量和裁决都有记录；基础设施故障与任务失败分开 |

第一版不训练基础 LLM，不自动新增领域专家，不搜索任意模型架构，不训练研究员的实验选择策略。已有游戏、部署监控与 hooks 代码保留；只改动业务闭环实际需要的部分。

RSI 在本阶段的可验证含义是：更新后的策略参与后续执行，改变反馈，再驱动下一轮更新。它证明反馈驱动的迭代改进，不单凭此循环宣称改进算法本身已学会改进自己。元研究策略留到业务收益成立以后。

## 2. 优化对象与边界

被评对象是一份完整 agent 版本：基础模型与推理设置、prompt、工具与工作流程、决策点规格、小模型及执行策略。评分评价任务结果，不分别给这些组件打分。

| 部分 | v0.4 可变范围 | 约束 |
|---|---|---|
| 基础模型 | 启动时选择目标模型并冻结；研究路由时才开放固定的小集合 | 模型 ID、供应商、版本、effort、fallback、采样设置进 manifest；更换即新实验 |
| Prompt / workflow | 根据 train/dev 失败做有限修改 | 不含任务 ID 对答案查表、隐藏断言或测试答案；有效方案可直接保留 |
| 决策规格与输入 | 修改已接入点的可见状态表示、问题与候选说明 | 不增加未来信息；不通过改措辞改变环境真值；变更标签语义须重建对应数据 |
| 小决策模型 | 一个模型或适配器，从一个决策点开始；迭代数据和配方 | 预先固定参数、上下文、推理与训练预算；复用训练器插件 |
| 领域能力 | 已有专用模型可作为固定工具 | 第一版不自动生成专家模型集合；新增能力必须有明确接口、反馈与净收益 |
| 工具与评测 | 业务工具表面、权限和评分语义冻结 | 可以改使用流程，不能改工具语义、环境真值、断言或评分分母 |

不要求每轮训练或只改一个键。候选可包含实现同一假设所需的多个改动，记录完整差异。提出具体组件的贡献主张时，才增加相应对照。

核心决策点由 harness 在确定位置调用。工具形式可以用于已有接口，但不能依赖 agent 偶然想起调用决策器。输入不支持、模型弃权或服务失败时，走声明的默认策略；实际执行路线必须记录。

## 3. Benchmark 与领先模型比较协议

### 3.1 数据、划分与可见性

[AutomationBench 官方仓库](https://github.com/zapier/AutomationBench)提供业务模拟环境和公开任务；本地公开任务与[官方榜单](https://zapier.com/benchmarks)的私有任务集不同。本地分数不能直接用于宣称超过官方榜单。

1. 固定上游 commit、依赖锁、任务文件摘要、工具模式、步骤上限和评分器版本。先 Marketing，其他域随后进入独立实验。
2. 首次观察结果前，按任务或工作流家族固定 `train / dev / test` manifest。变体、同任务的全部轨迹、分支、重复尝试和标签属于同一组；随机种子或 session ID 不构成新任务。
3. train 用于采集和训练；dev 用于诊断、prompt 搜索、选模型和候选晋升；test 只用于锁定最终版本后的报告。训练池内部再按任务组划分 checkpoint 验证及必要的校准数据。
4. 先记录实际分组数量和区间宽度，再判断可支持的主张。小样本可报告探索性结果，不能用同任务重复次数伪装独立任务数量。
5. 研究员只看 train/dev 证据。执行 agent 只看任务和合法工具返回，不看评分断言、参考答案、未来状态或离线分支结果。
6. 公开测试可下载，因此隔离指本实验的访问与调优协议，不承诺基础模型预训练未接触过这些内容。

test 不参与继续迭代、挑种子、挑最好一代或发布与否的筛选。根据其结果修改方案后，该池转为开发资料；新的泛化结论需要新的独立任务。每代曲线来自 dev，最终测试单独显示。

### 3.2 比较对象

外部能力参照是**业界领先模型**。实验开始时，依据目标域的官方结果选择至少两家供应商的领先模型，记录日期、来源与实际可调用的模型 ID。2026-09-27 官方 Marketing 页面列出的候选包括 GPT 6 Astra（Max）与 Claude Opus 5.5（default fallbacks, Max）；这是候选选择快照，启动时重新核验，不把官方私有分数写成本地成绩。

领先模型也通过同一个任务驱动器运行，获得完整说明、正常工具发现方式及各自支持的合理提示格式，不故意削弱基线。fallback 要显式配置并计入全部模型成本；无法复现官方 fallback 时另行命名。模型不可用时记录缺席，不能悄悄换成弱版本。

| 版本 | 目的 | 最小要求 |
|---|---|---|
| `frontier_a / frontier_b` | 最终能力相对领先模型的位置 | 相同任务、工具、评分器；公布模型、effort、预算、fallback |
| `base` | 判断整套迭代是否有效 | 目标底座的合理初始 agent，不刻意设置弱 prompt |
| `prompt_best` | 判断训练是否值得 | 同一目标底座，允许预算内已优化的 prompt/workflow，不启用学习得到的决策器 |
| `evolved` | 最终方案 | 开发阶段锁定的完整版本，记录全部优化与训练支出 |

`base` 与 `prompt_best` 无差异时可复用。同底座比较固定模型、effort、工具权限和每任务资源上限。检验小模型增量时使用同一最终 prompt/workflow，将决策器替换为声明的默认策略；若这就是 `prompt_best`，直接复用，否则只在提出小模型贡献主张时补这一对照。预算上限一致，实际花费差异照实报告。

跨模型报告两种视角：相同工具和步骤上限下的任务能力，以及预先声明费用上限下的质量—成本取舍。不同 tokenizer、缓存和计费方式导致 token 数不能简单等价。领先模型在费用上限内没有可运行配置时，报告缺口并展示正常配置的能力和成本，不能将其记成失败制造胜出。

### 3.3 指标与结论

- **主指标：完整任务通过率 `task_completed_correctly`。** 保持官方断言和评分语义。
- **辅助指标：`partial_credit`、错误类型、约束违反次数。** 部分完成率不能称为任务成功率。
- **运行成本：** 主模型、fallback、决策模型、特征准备、额外验证和重试的全部开销；另报延迟、工具次数、预算耗尽。
- **改进成本：** 数据生成、离线分支、研究员、训练、开发评测与无效作业。报告累计值；摊销时公开任务量假设，未测费用标记缺失，不能视为零。
- **统计：** 预先固定重复次数、比较对象和主要结论。按任务聚合重复运行，配对比较；有家族依赖时按家族重采样。报告差值与区间，中途增加实验次数要记录。

“能力更强”要求预先指定的完整任务通过率比较有支持；“更经济”要求质量满足预先声明的非劣界限且成本降低。“差异不显著”不等于同等质量。达不到就报告未证实或仍落后，不承诺必须赢、不预填分数、不换指标补结论。

三项证据分别记录：**C1 迭代相对同底座起点的收益；C2 相对领先模型的能力或成本位置；C3 小决策模型相对同配置默认策略的增量价值，以及是否值得替代 prompt_best。** C2 单独成立不足以证明迭代有效；C1 成立而 C3 不成立时，只能证明整体优化有效。只关闭决策器能衡量它在当前配置中的贡献，但不能把一份较弱 prompt 上的收益说成优于已有最佳 prompt 方案。

## 4. 如何产生可学习的改进

### 4.1 从失败选择决策点

基线先完整运行，再按证据选择第一处干预。候选包括空搜索后的处理、是否补充业务规则、是否验证写入、是否继续处理、是否升级模型。它们是待验证假设，不是第一版全部要做的功能。

一个点进入训练须满足：频繁且有结构；当时可见信息足以判断；选择能改变后续结果；反馈可获得；价值有机会覆盖额外开销。明确的 API 参数约束先写成规则。依赖复杂长程推理的判断，不因选项少就强交给小模型。

先在少量 train/dev 状态做有限干预，观察是否存在改善结果的选择，再投入训练。事后知道结果的最佳选择只用于检查机会，不作为可部署成绩，也不保证模型能学会。

### 4.2 三种数据不能混用

| 数据 | 用途 | 可否直接进入现有监督训练 |
|---|---|---|
| 当时观察、动作、工具结果、模型与版本 | 重建过程、构建输入 | 没有标签时不能 |
| 最终通过率、部分完成率、用量 | 评价完整方案、诊断失败 | 不能展开为每一步的正确标签 |
| 对特定决策有依据的动作标签或偏好 | 训练决策模型 | 经过来源、语义、分组与噪声检查后可以 |

当前 `ledger.Row.target` 和 `evolve/build.py` 接受候选标签分布。接入需要明确的反馈构造器，不能把任务 reward 改名为 label。样本保存决策前输入、候选、动作、来源任务组、策略版本、反馈证据与信号生成版本。

优先支持两条信号路径：

1. **局部可核验结果。** 对训练任务的隔离状态事后检查是否满足完成条件。训练的是完成判断，不是“继续一定有收益”的真值；最终评测任务的在线执行不能得到此类评分反馈。
2. **有限分支比较。** 在训练任务的同一决策前状态尝试少量替代动作，用固定后续策略、剩余预算及预定重复次数执行到底，比较完整结果与成本。环境无克隆接口时，先验证 reset 加动作前缀重放可重建同一状态；不等价重放不能当配对证据。差异不明确时弃权或保留不确定性，不把一次偶然成功当永久正确标签。

分支标签依赖后续模型、prompt 与预算，条件变更后须重验适用性。分支成本计入改进预算。标签来自隔离环境观测或人；LLM 可提诊断与候选，但其自评、参考轨迹相似度、晋升结论都不直接作为业务动作真值。保留现有 `env/human` 与 `EVAL_ONLY` 区分。

最终 reward 直接驱动策略梯度属于另一种训练契约，第一版不引入。无法形成有用信号时保留有效 prompt、换干预点或报告假设失败，不能用扩大模型规模掩盖信号缺口。

### 4.3 一轮实验与多轮运行

1. 当前版本在 train 执行，写轨迹、决策与结果，使用唯一任务组映射。
2. 研究员读 train/dev 失败和历史开发实验，提出一个有依据的候选或弃权。
3. 校验改动、证据、数据和预算；准入后冻结候选 manifest 与开发评测计划。
4. 需要训练时构造标签或分支样本，按任务组拆 train 内部数据，复用 build/check/train/store/serve；prompt 候选跳过训练。
5. 在 dev 重新执行完整任务。小规模筛选与完整开发评测分开记录，不能比较不同任务子集的均值选冠军。
6. 按事先约定的任务效果和预算规则接受或拒绝；证据不全是 `inconclusive`。选定完整版本后才更新指针。
7. 新版本回 train 采集。预算耗尽、预定无收益耐心耗尽、无可执行提案或持续基础设施失败时停止。
8. 开发结束，锁定最终方案和对照，按预定全部重复次数跑 test，无论结果正负都报告，不从 test 挑最好一代。

dev 分数是搜索过程证据。晋升门减少无依据替换，不能保证真实分布单调进步，也不能凭“一候选一裁决”保证整个自适应搜索的错误概率为 5%。

### 5.1 最小运行契约

任务结果至少包含 `task_id, family_id, split, attempt_id, candidate_ref, manifest_hash, success, partial_credit, usage, elapsed, termination, validity, evidence_ref`。决策记录关联 `point, observation_ref, candidates, action, default, executed_by, feedback_ref`。

候选 manifest 补足现有发布三元组：基础模型及采样身份、prompt/workflow hash、决策规格、模型 ref、执行策略、环境/工具/评分器版本、预算和数据 manifest。一个任务固定一个版本；候选评测使用隔离 runtime，不提前替换冠军。缓存键含完整语义身份，复用仅限预定开发证据；最终报告说明哪些是新执行。

### 5.2 现有机制的处理

- `stop.py` 在带 checker 的 `on_finish` 路径由 checker 决定。接入须证明决策模型实际改变执行；官方评分器不能作为在线 checker 暗中纠错。
- 接管策略依赖局部标签、校准和 session 风险。benchmark 策略不自动继承“业务风险最多 5%”保证；没有相应标签时不能计算该风险。task profile 的阈值或回退策略在开发阶段固定，整体效果通过任务结果判断。
- 复用 `GateRecord`、并发更新保护、版本与账本。task profile 按任务 manifest 组织评测，不伪造局部标签通过旧门；原 profile 的限制和测试保留。
- 模型自报完成、预算耗尽、错误操作属于有效任务结果。环境起不来、服务中断等是无效尝试；按固定规则记录并补跑，不删除有效失败。未补齐的正式比较不发布单一胜负结论。
- 模拟操作只作用于隔离数据。真实业务部署另行评估，不能由 benchmark 分数推导已可安全上线。

## 6. 预算与防膨胀

每个实验预设 `max_candidates`、`max_rounds`、`max_trainings`、`max_branch_rollouts`、模型规模、单次与累计费用/时间上限。估算用于准入，实际用量用于停机与报告；缺失费用以 token、GPU 时间及缺失原因保留，不能当作免费。

一轮默认一个候选，明确需要少量方案比较时才扩。无需先完成大规模消融、游戏特征搜索、多模型专家系统、元研究模型、实时 dashboard 或新云调度。保留一个主指标、一份完整版本、一套运行和反馈协议。

新增模块必须回答：解决哪个观察到的失败，最简单替代是什么，如何按完整任务效果决定保留或删除。prompt 已达到目标而训练无增量时可交付有效方案，但报告 C3 尚未成立。

## 7. 交付与验收

首个可发布实验提供：

1. 固定环境、任务分组、模型与推理设置的配置和复现命令。
2. 至少两种领先模型的本地同条件比较，以及 `base / prompt_best / evolved` 必要对照；缺席配置明确标注。
3. 开发阶段全部候选结论与版本曲线，一次完整反馈—更新—再执行的证据。
4. 锁定版本的独立测试：成功数/任务数、重复次数、差值区间、运行与累计改进成本。
5. 前后执行回放、模型卡与标签来源、manifest、候选差异、机器可读报告。

工程闭环完成与 C1/C2/C3 被证实是不同状态。未证实的项如实记录，报告不预填收益。预算只支持探索性结果时，以该范围发布，不声称全 benchmark、官方 SOTA 或跨业务普遍成立。

扩展顺序：Marketing 闭环 → 独立测试与领先模型比较 → 更多业务域 → 其他公开环境。贪吃蛇保留为本地 smoke 与回归检查，不再承担主能力证明。

## 8. 参考依据

- [AutomationBench 官方数据、评分与接口](https://github.com/zapier/AutomationBench)：环境、固定评分与公开/私有边界。
- [AutomationBench 官方榜单](https://zapier.com/benchmarks)：领先模型选择；每次实验记录日期与身份。
- [RouteLLM](https://arxiv.org/abs/2406.18665)：学习有限模型选择的可行性，不代表所有控制决策已解决。
- [Budget-Aware Agentic Routing](https://arxiv.org/abs/2602.21227)：多步决策考虑后续结果与预算；其结果不替代本项目实测。
- [GEPA](https://arxiv.org/abs/2507.19457)：执行反馈可以直接改进 prompt，训练应与已有有效方案比较。
