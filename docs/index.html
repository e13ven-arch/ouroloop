Bounded recursive self-improvement · of the harness, not the model

A self-improving agent rewrites its own harness, and proves each change live.

When a request comes back returned, a Revision Session reads the agent's own run, changes its Harness Package — tools, hooks, skills, prompts — and a Live Probe runs the same request for real. Only an accepted probe is adopted, and only for that task. The session is never shown an answer.

The loop

One returned request, one session, one proof.

Every step is host-run except the edit. The host decides what the session is told, whether a candidate is admissible, whether a probe is accepted, and what is adopted.

host

Returned

The first encounter runs the task's package. Accepted: finished, never revised. Returned: a session opens.

session

Revision Session

Reads the Run Digest, the Source Inventory, the Rejected Checks and the Experience Library. No score, no expected value.

host · deterministic

Admissible?

Within the Package Contract; no literal that belongs to one task; actually changed. No model asked.

worker

Live Probe

The candidate runs the same request for real, on a fresh world. Bounded; the same tree is never probed twice.

host

Per-Task Adoption

The last accepted candidate, as it ran, becomes this task's package. None accepted: it stays. No judge, no person.

Architecture

Four things, and a line between them.

S = (W, R, E; K): the package a session may change, the session that changes it, the transcript it reads, and the Frozen Core that bounds all three.

Figure 1 · the Frozen Core holds four invariants; the worker is a boundary, not a component; adoption is applied by the host, outside the session.
W · Harness Package

The only thing that changes

  • Agent loop, tools, hooks at six sites, prompts, skills, config, one manifest
  • W₀ is the base; W_t is one task's adopted package, else W₀
  • Fixed shape; prompts may only grow; the manifest must equal the diff
R · Revision Session

Told little, must prove much

  • Acceptance Signal, Rejected Checks, Run Digest, Source Inventory
  • Edits a copy; the candidate is taken as the diff, never as its claim
  • Proves it with a Live Probe in the isolated worker
K · Frozen Core

Fixed for the whole loop

  • Host-Side Scorer: grading rows never leave the host
  • Feedback Tier: the one boundary; never an expected value
  • Package Contract: no answer in the package. Bounds no session can raise
How one improvement happens

Every run passes through the scorer. Every rule is a gate.

Two return edges: probes left, the session tries again with the probe's run beside the first; and the Experience Library, the only channel between tasks.

Figure 2 · the worked example beneath the flow is a quarterly tax estimate drawn from one real trace: the session built a source-coverage guard, a routing guard and an estimate tool; the third probe was accepted and held.
Feedback tiers

What the session may be told is a field of the protocol.

Every tier carries the Run Digest and the Source Inventory as counts. The tiers add only what is listed; the grading rows stay on the host at every tier.

FAQ

Plain answers.

What is reharness?

An open-source self-improving agent harness: a bounded form of recursive self-improvement in which an LLM agent's own model revises the harness the agent runs in — tools, hooks, skills, prompts — from the agent's own returned runs, and proves every change with a live run before it is adopted.

Is this recursive self-improvement?

The bounded kind. The agent's model improves the agent's harness; the weights, the scorer, the feedback tier, the package contract and the bounds are frozen, and the Revision Session that makes the change is not itself improved by the loop.

What is an agent harness?

Everything around the model that makes it an agent: the loop, the tools it may call, the hooks before and after model and tool calls, its skills, prompts and config. reharness treats that as one versioned package with a fixed shape, and changes only that.

How is this different from fine-tuning or prompt optimization?

No weights change and no prompt is optimized against a score. A change is harness engineering — a guard, a tool, a skill — written by a session that read the failing run and was never shown the answer, adopted only after a live run on the same request came back accepted.

What does the session learn?

Habits, not answers: open every unread source before writing, derive figures by code, route a derived value through a tool. These appeared in independent sessions with none of the words in the prompt.

Can I run it on my own agent and tools?

Yes, through an adapter. The benchmark's tasks, tools and scorer sit behind one adapter; a real business tool set fits behind the same Package Contract.

Install

Three commands, then a run.

Python 3.11+, Docker for the isolated worker, headless Claude Code for the agent and the session. The smoke and freeze steps cost nothing; a repeat run calls a model.

# install
git clone https://github.com/e13ven-arch/reharness && cd reharness
pip install -e .

# checks at no cost: splits, scorer contract, the seed's literals
reharness bench --config examples/automationbench/quickstart-repeat.toml --phase smoke --checks-only

# freeze K and the Sealed Protocol, then run the repeated-request loop
reharness freeze --config examples/automationbench/quickstart-repeat.toml
reharness bench --config examples/automationbench/quickstart-repeat.toml --phase repeat --arm learn
reharness bench --config examples/automationbench/quickstart-repeat.toml --phase report
