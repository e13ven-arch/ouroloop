# StarHarness (ServiceNow) — deep read for reharness

Sources used: repo https://github.com/ServiceNow/StarHarness (main, HEAD = a56d8f6, 2026-09-24), its files read raw (copies under /private/tmp/claude-502/-Users-leon-workspace-reharness/c9591706-bc88-4f6c-9900-8380bdb28477/scratchpad/starharness/), paper https://arxiv.org/abs/2608.24804 (v1, 2026-08-25), and the critique it cites, https://arxiv.org/abs/2607.12227. File line numbers below refer to the repo files at HEAD. Items I could not verify are marked "not stated" or "unverified".

## 1. What it modifies

- Harness only; model weights fixed. Editable set per adapter (`editable_dirs`): `benchmarks/<name>/` plus the whole vendored agent framework `vendor/stirrup/` (https://github.com/ServiceNow/StarHarness/blob/main/benchmarks/automationbench/benchmark.py lines 33–34; ITBench the same, benchmark.py lines 32–33). Inside that, the proposer may change: tool descriptions, pydantic parameter schemas, executor wrappers (retry/validation/post-processing), the tool list (add/remove tools), sub-agents via `Agent.to_tool()`, skills (SKILL.md dirs), the finish tool, tool providers, Stirrup agent-loop internals (`core/agent.py`: turn handling, summarization, overflow recovery, continue-injection, turns-remaining warnings), the LiteLLM client layer, prompts (`prompts/*.txt`), and constants (`CONTEXT_SUMMARIZATION_CUTOFF`, `TURNS_REMAINING_WARNING_THRESHOLD`) — the enumerated catalog is `surfaces.md` (https://github.com/ServiceNow/StarHarness/blob/main/benchmarks/automationbench/surfaces.md).
- Not editable (`out_of_scope`): adapter, config, grader, data loader, evaluator, progress/trace logging, the three split JSONs, `domain_spec.md`, `surfaces.md`, and both proposer prompt files `proposer_prior.md` and `propose_task.md` (benchmark.py lines 37–53). So the improver's own prompts are explicitly protected: not self-modified.
- Paper's own list of the evolved surface: "prompt and task framing, tool interfaces, skills, MCP-backed providers, subagent structure, and agent-loop configuration" (abstract, https://arxiv.org/abs/2608.24804).

## 2. The improvement loop

- Proposer: oh-my-pi (`omp`, a Pi-harness-derived coding agent CLI) run non-interactively with `-p --approval-mode yolo --model openai/gpt-5.4 --thinking medium --no-skills --max-time 2400`, cwd = the repo root (https://github.com/ServiceNow/StarHarness/blob/main/omp_wrapper.py lines 218–235; evolving_harness.py lines 705–709). Paper: GPT-5.4 (medium) is both agent-under-test and proposer (Sec. 4).
- One candidate per iteration, hill-climbing on a single frontier; no population or archive. "Each iteration is one coherent change" (proposer_prior.md line 29). Fixed iteration count `--iterations` (default 5; domain_spec.md: "Optimization budget: fixed N = 5 iterations per run", "Stopping: fixed N iterations"). Paper Algorithm 1: budget B iterations, one patch Δ per iteration (paper Sec. 3.1).
- Lineage: git. Baseline committed; each kept candidate is a commit `iter{i}: {name} ({hypothesis})` (evolving_harness.py line 888); rejected candidates are reverted with `git checkout -- <editable_dirs>` + `git clean -fdq` (lines 239–246). Frontier state in `evolving_runs/<run>/frontier.json` (commit sha, selection mean, per-task, verifier rate, kept hypotheses); ledger in `evolution_summary.jsonl`; patches in `candidates/iter{i}.patch`.
- After a keep, the search split is re-run with the new frontier to refresh the proposer-visible traces (lines 875–887).
- Paper additionally describes a tree-search mode (nodes with parent links, merge/debug/improve operations) used only on EnterpriseOps-Gym as a sequential exploration stage before hill climbing ("8 accepted patches came from the tree-search exploration stage and 4 from the subsequent hill-climbing stage", Sec. 5). Tree search is not in the repository: `grep -ri "tree.?search\|ledger" ` over the non-vendor code returns nothing, and `evolving_harness.py` is hill-climb only. Unverified whether it will be released.

## 3. Evaluation and selection

- Three disjoint splits: search (proposer-visible), selection (hidden validation), holdout (final only). Checked-in sizes: AutomationBench Finance 30/20/50 of 100; ITBench SRE 5/5/30 of 40 (counts verified from the JSON files; README table https://github.com/ServiceNow/StarHarness/blob/main/README.md lines 111–114). Disjointness/emptiness validated in `BenchmarkAdapter.validate_scenario_sets` (benchmarks/base.py lines 149–181).
- Repeats: `--repeats` default 1 (evolving_harness.py line 509); domain_spec.md: "Repeats: 1 per task (AA methodology)"; ITBench domain_spec: "Default repeats: one during evolution; use more repeats for final measurement" (the loop passes the same `args.repeats` to the held-out run, line 915, so by default the final is also 1 repeat). Turn cap: 50 for AutomationBench (AA), 100 for ITBench.
- Acceptance rule (deterministic, code lines 336–345 and 406–420): keep iff selection mean > frontier mean + 1e-9, or mean tied within 1e-9 and verifier rate strictly higher. Verifier rate = guardrail-intact fraction for AutomationBench (benchmark.py lines 208–210); ITBench has none, so ties never advance. No minimum effect size, no significance test, no repeats requirement. Per-task regressions and "below baseline" lists are computed and logged but "recorded as diagnostic evidence, not as independent vetoes" (domain_spec.md Sec. 3).
- Pre-gates before paying for the selection run: (a) scope/guardrail check on the diff, (b) import check of every benchmark adapter (so a `vendor/stirrup` edit that breaks another benchmark is rejected; lines 278–304), (c) smoke: first search task, 1 repeat, `--smoke-max-turns 20` (line 772), (d) optional "test flip": run the proposer's self-chosen `test_scenario`; `validated` iff it goes from <1.0 to 1.0 (lines 778–817), then (e) an LLM "proceed gate" (another omp call) decides whether to spend the full selection eval (lines 440–489, 819–838). Code comment: "a failed probe is not an automatic rejection" (line 524). The paper's Algorithm 1 says the opposite: "if test flip fails: revert and record rejection" (Sec. 3.1). Code and paper disagree here.
- Final: one held-out run of the winning commit, written to `held_out_result.json` (lines 910–921). No sealed plan, no confidence interval, no variance reported anywhere in the paper (all tables are single point estimates; paper reports no seeds or repeats for the final).
- Summary integrity: `read_summary` rejects missing/duplicate tasks, non-finite scores, or an aggregate that does not match the per-task mean, so a partial run cannot enter the frontier (benchmark.py lines 151–210).

## 4. Leakage controls (does it evaluate on tasks the proposer never saw?)

- By design yes: selection and holdout tasks are disjoint from the search tasks the proposer reads, and the proposer is given full assertions/ground truth, per-assertion `score.json` and full `trace.log` only for search tasks (`gather_traces`, benchmark.py lines 250–286).
- Diff guards: reject edits to out_of_scope files, any changed path containing `ground_truth`, edits outside `editable_dirs`, and added lines containing forbidden substrings (`task.assertions`, `task.raw_info`, `task.task_id`, `load_tasks(`, `benchmarks.automationbench.grader`, `summary.json`, `score.json`, ...) or any quoted known task ID across all three splits (benchmark.py lines 220–248). The evaluator passes an assertion-free `AgentTask` to editable code (data.py; tests `test_agent_task_hides_grading_data_and_copies_state`).
- Weak points (my reading of the code, not claimed by the authors): the proposer runs as a yolo coding agent in the repo root; `selection_scenarios.json`, `holdout_scenarios.json`, the full 100-task dataset under `vendor/automationbench/`, and the selection runs under `runs/evolving_<run>_base_selection` and `runs/evolving_<run>_iter<i>` are all on disk in its cwd. Hiding is by instruction only ("Do not inspect selection-split result JSONs or selection scenario definitions while proposing", propose_task.md line 23). Further, `evolution_summary.jsonl`, which the task prompt lists as a "useful artifact" (propose_task.md line 27), records each candidate's selection `per_scenario` scores (evolving_harness.py line 851, written at line 727). That contradicts the paper's "no selection-task contents, traces, verifier feedback, or per-task outcomes" (Sec. 3.1) at least for per-task selection scores of rejected candidates.
- The paper's own generalization evidence: evolution-set gain vs held-out gain for GPT-5.4: ITBench +45.0 vs +31.7, EnterpriseOps-Gym +22.0 vs +15.1, AutomationBench +23.0 vs +29.3 pp (Table 2). Headline "full-benchmark" numbers (Tables 1, 3–5) include the search and selection tasks.

## 5. Is the improver improved?

No. `proposer_prior.md` and `propose_task.md` are in `out_of_scope`; the proposer model/harness is fixed; the stratifier is a one-off pre-evolution run. The paper describes no meta-level loop and no comparison of proposer variants. The only adaptive element is the ledger of kept/discarded hypotheses fed back into the prompt (Sec. 6 below).

## 7. Failure modes they report

- No Limitations section. Acknowledged: a search-to-held-out gap (Table 2); ITBench regressions "when upstream search continued after a proximate cause should have ended it"; "we cannot isolate the causal contribution of any individual patch" (Sec. 5).
- Not discussed: evaluation noise, reward hacking/grader exploitation, variance. domain_spec.md notes the published AutomationBench baselines were measured with gpt-5.5 while evolution ran gpt-5.4, and lists open questions on endpoint rate limits and proposer context size for 30 full traces.
- Structural noise exposure (my analysis): 1 repeat × 20 selection tasks (5 on ITBench) with "any strictly positive delta" acceptance means a single assertion flip promotes a candidate; ITBench's granularity is 20 points per task.

## 9. Agent and harness design

Agent loop (Stirrup `Agent`, `vendor/stirrup/src/stirrup/core/agent.py`): a single ReAct-style loop, no planner/executor split, no cross-task memory (fresh `Agent` and fresh `WorldState` per task/repeat, agent_setup.py lines 133–145). `run()` loops while turn < `max_turns` (lines 1429–1498): one `client.generate(messages, tools)` → execute every requested tool call sequentially → append messages. Tool protocol: native tool calls with pydantic schemas (`Tool(name, description, parameters: BaseModel, executor)`); tool exceptions are returned as tool content so the agent self-recovers (agent_setup.py lines 59–77); no tool-call retry. Finish: a `finish` tool is auto-added and must be called in its own turn (base prompt: "You will need to call a finish tool as your last step"); calling two finish tools in one turn rejects both (lines 1243–1269); the default finish executor verifies listed output files exist (tools/finish.py). Stop/budget: turns-remaining warnings injected as user messages when ≤20 turns remain and "This is the last turn" at 1 (lines 100–106, 1439–1442); `max_turns` reached → `finish_params=None`. Context management: LLM summarization when `token_usage.total / client.max_tokens ≥ 0.7`, with a structured summary prompt, a bridge message and a synthetic "Got it, thanks!" user turn (lines 1283–1314, prompts/message_summarizer*.txt); context-overflow recovery drops the latest completed turn and retries (lines 1455–1457). "Please continue the task" is injected when the model answers without tool calls (lines 1489–1497). Retries live in the client: tenacity, up to 3 attempts on Timeout/APIConnectionError/RateLimitError/APIError, 300 s request timeout (clients/litellm_client.py lines 97–113). Sub-agents via `Agent.to_tool()`; skills = SKILL.md metadata injected into the system prompt (the agent is expected to `cat` the file, which requires a code-exec tool the AutomationBench agent does not have — my inference). System prompt = base template with `max_turns` + interaction note + input files + skills + "Follow these instructions from the User:\n{task system prompt}" (lines 642–688). There is no hook/middleware system; "middleware" means wrapping tool executors or editing the loop code.

AutomationBench wiring: three tools `api_search`, `api_fetch`, `base64_encode` over an in-process `WorldState`; system prompt is the task's embedded prompt verbatim; 50-turn cap; grader runs assertions against final state (aa_score: 0 if any guardrail broken else objectives passed/total; strict `task_completed_correctly` also recorded) (run_eval.py, domain_spec.md Sec. 1).

Change representation and lifecycle: the proposer edits files in place; the loop captures a unified git diff scoped to `editable_dirs` as `candidates/iter{i}.patch` plus a `pending_eval.json` {name, hypothesis, changed_files, test_scenario} (proposer_prior.md lines 54–67); kept = commit (linear lineage), rejected = checkout+clean; stray files outside scope that the proposer created are deleted unless protected (lines 216–237). Isolation/sandboxing: none beyond git scope — README: "The proposer executes model-generated code with your local user permissions. Use a dedicated checkout or sandbox" (README.md lines 216–219); candidate harness code runs in the same venv via editable installs, so a `vendor/stirrup` edit is live immediately; pre-use testing is the import check, the 1-task ≤20-turn smoke, and the optional test-flip.

## 10. Self-improvement design

- Signal: per search task, the ground-truth assertions, per-assertion pass/fail with params (`score.json`), the full conversation trace, current vs baseline per-task search scores, and the ledger of kept and discarded hypotheses with reasons (render_task, benchmark.py lines 288–331; evolving_harness.py lines 655–699). ITBench additionally gives the ground-truth root causes.
- Diagnosis: aggregate by instruction — "aggregate across tasks to find the recurring failure pattern ... not the quirks of any single task" (propose_task.md lines 36–42). Optional `--trace-analysis subagents` mode spawns one isolated omp subagent per search trace that reports "the first causal agent error, recurring failure candidates, supporting trace evidence, and a general harness intervention"; the parent aggregates and makes one edit (lines 117–141). Pre-evolution, a separate stratifier labels each baseline trace's causal failure mode with one subagent per trace and selects the smallest search/selection sets covering every failure mode with matched score and verifier distributions (stratify_tasks.py, validated by `validate_plan`).
- Avoiding refuted ideas: the prompt lists KEPT (with delta) and every DISCARDED/REJECTED/ABORTED attempt with name and hypothesis, and instructs "Don't repeat discarded attempts without a meaningfully different hypothesis" and "If a surface has been exhausted, pivot" (proposer_prior.md lines 29–31; propose_task.md lines 44–47). No automatic novelty check, no embedding/archive; the ledger is the jsonl file.
- Stop: fixed iteration count only; no plateau detection, no budget ledger (proposer cost per iteration is logged from omp's session but never enforced).
- Proposal site choice: the proposer is told to pick a family (prompt vs structural) from the catalog based on the diagnosed failure mode; the paper's taxonomy of what actually got accepted is interface repair, environment conventions made explicit, and operational knowledge/search compression (calculators, triage steps, forensics overview) (Sec. 5).

## Takeaways for reharness

- Borrow: (1) failure-mode-stratified split construction — label each baseline train/dev/test failure before any evolution and check that dev and test have matched failure-mode and score distributions (reharness's hash split, seed 1, is unmatched; with 25/23 tasks a lucky split is a real risk); keep the labels train-blood only. (2) A cheap triage stage before the paid dev gate: import check across all consumers plus a 1-task short-turn smoke of the assembled package, and optionally a proposer-nominated "should flip" train task — used as evidence for a go/no-go on spending the gate, never as a veto. (3) An explicit per-domain `surfaces.md`-style catalog of mutable surfaces with current defaults and two change families, so R diagnoses first and then picks prompt vs code; v0.2's accepted changes were all end-of-task/pre-write checks, which suggests R is under-exploring tool-wrapper surfaces. (4) A forbidden-substring + task-ID regex guard on added lines of generated package code as a cheap leakage check alongside the Docker isolation. (5) Report turns, tool calls and cost per attempt next to the score as StarHarness does in Tables 3–5 (reharness already logs these).
- Already better in reharness: a sealed, committed final plan with paired bootstrap intervals (StarHarness: one held-out run, 1 repeat, no CI, no sealed plan); a gate with `min_gain` and regression tolerance (StarHarness accepts any >1e-9 delta on 20 tasks × 1 repeat, 5 tasks on ITBench, regressions non-binding); enforcement-based hiding (R's context is filtered by fixed code; StarHarness hides selection/holdout by prompt instruction while the files and per-task selection scores sit in the proposer's cwd); Docker-isolated package execution with a tool broker (StarHarness runs proposer and candidates with local user permissions); a budget ledger and reservation accounting (StarHarness has fixed iterations only); and the R-recursion slot, which StarHarness forecloses by protecting the proposer prompts.
- Trap: strict-improvement acceptance with single repeats. reharness measured the same W0 at 41.3% and 47.8% on identical test runs; a StarHarness-style gate would promote noise and inflate "accepted patches". Do not lower `min_gain` or repeats to get more accepted changes per cycle.
- Trap: opening the agent-loop core (the whole `vendor/stirrup`) as an edit surface. It yields their biggest wins (interface repair, calculators) but every change is unsandboxed Python with cross-benchmark blast radius; if reharness widens the package surface toward loop internals, keep it behind the fixed package API, Docker worker, import+smoke checks and the frozen component kinds in K.
- Trap: the critique StarHarness itself cites, Wang et al. 2026 (https://arxiv.org/abs/2607.12227): harness evolution "does not consistently outperform simple test-time scaling methods and exhibits limited generalization" unless compared against task-level search under matched feedback and inference budgets. reharness's final already fixes per-attempt limits for W0 and W*, but the report should say explicitly that the $81–$303 evolution spend is extra search budget and that no matched test-time-scaling baseline has been run.
