## (2) Improvement loop
- Per generation: `choose_selfimproves` samples `k` parents from the archive (default `--selfimprove_size 2`, SWE-bench; paper k=4 for Polyglot) with replacement, weight `w_i = sigmoid(10·(α_i−0.5)) · 1/(1+children_i)` (code `score_child_prop`; paper Appx C.2 eq. 1–7, λ=10, α0=0.5). Paper's eligible-set filter α<1 is not in the code. — https://github.com/jennyzzt/dgm/blob/a565fd2/DGM_outer.py#L50-L150
- Per parent, one "entry" is chosen: SWE-bench: 25% `solve_empty_patches` (if ≥10% empty patches), else 25% `solve_stochasticity`, else 25% `solve_contextlength` (if a repeated "Input is too long" error exists), else ONE random unresolved task id. Polyglot: 25% stochasticity prompt, else an empty/unresolved task. — same file L112-L150; `get_diagnose_prompt_polyglot` L362-L368
- One child per parent per generation; `--max_generation 80`. Paper: "80 iterations (generating one new agent per iteration), with two iterations running in parallel for SWE-bench and four for Polyglot"; code defaults (80 × k=2) would yield 160 attempts — ambiguity unresolved. Hallucination case study: 150 iterations (Appx H).
- Archive: `keep_all` by default; every child that "compiles" is kept regardless of score (`is_compiled_self_improve`: has performance keys, ≥1 non-empty patch, evaluated on ≥10 tasks). A `keep_better` mode with `noise_leeway=0.1` exists but is not default. Lineage stored as per-run `metadata.json{parent_commit}` + `model_patch.diff`; a child is materialized by applying ancestor diffs in order (`get_model_patch_paths`). — https://github.com/jennyzzt/dgm/blob/a565fd2/utils/evo_utils.py
- Baselines: `no_selfimprove` (base agent always does the modifying), `no_darwin` (always last commit, no archive); `DGM Greedy` (always best parent) in paper Appx A.3.

## (3) Evaluation and selection
- Staged, same tasks for everyone: 10 tasks (`swe_bench/subsets/small.json`, all django) to check basic code-editing; if resolved ≥ 40% of those 10 → 50 more (`medium.json`, django+sphinx), total 60. Paper adds: if >40% on 60 and top-2 of the archive → 200 tasks (140 `big.json` + the 60). In the released code `get_full_eval_threshold` (= max(0.4, second-highest fully-evaluated score)) is computed and passed, and `big.json` is loaded, but neither is used inside `self_improve`/`run_harness_swe` — the 200-task stage is not wired into the released loop (inferred from code; presumably run via `test_swebench.py --test_big`; unverified). — https://github.com/jennyzzt/dgm/blob/a565fd2/self_improve_step.py#L125-L178 , https://github.com/jennyzzt/dgm/blob/a565fd2/test_swebench.py
- Polyglot: 10 → 50 (`polyglot/subsets`); final numbers re-measured on the full benchmark (225 tasks per `initial_polyglot/metadata.json`).
- Repeats: `--num_swe_evals` default 1 — one run per task per candidate, temperature 1.0 (Appx D.1). No statistical test; the 40% threshold is "a heuristic chosen based on the noise observed in preliminary runs" (Sec. 4.2). Score = resolved/submitted (`get_all_performance`).
- Regression check: none at the harness level; SWE-bench PASS_TO_PASS is part of task scoring, not a gate on the agent. Only acceptance rule: compiles + ≥1 non-empty patch. No held-out final inside the loop; best agent = highest archive score on the search tasks.
- Timeouts: self-modification run `timeout 1800` (30 min); SWE task `timeout 32400` (9 h); Polyglot task 600 s + 120 s test; whole self-improve future 1.5 h (on timeout the child is dropped from the archive).

## (4) Leakage controls
- Weak inside the loop: the diagnosed failing task is one of the 10/60 tasks the child is then scored on, and the diagnoser prompt includes SWE-bench's "Private Test Patch" (`test_patch`) and the hidden test results for that task (`diagnose_prompt` fields; the prompt says the agent "should try to implement its own tests"). Paper Appx C.3 acknowledges: "While the private test patch is included in the diagnosis prompt, one could imagine… hard code the solutions… from manual inspection… we have not observed." Mitigation is only the instruction that improvements "should not be specific to any particular GitHub issue or repository." — https://github.com/jennyzzt/dgm/blob/a565fd2/prompts/self_improvement_prompt.py#L77-L120
- The reported 50.0% is on the 200 search/ranking tasks (selection-biased in-sample). Held-out evidence is only transfer: SWE-evolved agent on Polyglot 28.9% vs base 14.2%; Polyglot-evolved on SWE-bench 24.5% vs 20.0% ("truly held-out tests", Sec. 4.4); model transfer on the same 200 tasks (Claude 3.7: 19.0→59.5; o3-mini: 23.0→33.0); Python-only→other languages (Fig. 4).
- Open issue #35 (2026-07-28, no reply): Polyglot container exposes `/polyglot` with hidden tests and `.meta` reference solutions to the unrestricted bash tool; reporter "did not find exploitation" in the logs. — https://github.com/jennyzzt/dgm/issues/35

## (5) Is the improver improved, and how validated
- Partly. The *implementer* is the agent itself (`p.modify(p)`): the same `coding_agent.py` + tools + tool loop that solve benchmark tasks implement the self-patch (`coding_agent.py --self_improve` inside the container), so better editing tools/retries carry over to future self-modification. The *diagnoser* is a fixed external call to `o1-2024-12-17` with fixed prompts (`diagnose_model` in `self_improve_step.py`; paper C.3 "We chose to use OpenAI's o1"), hidden from the agent and never evolved; parent selection, archive and eval are fixed. Paper's "Each selected parent analyzes its own benchmark evaluation logs" (Sec. 3) overstates the code.
- Validation: only the ablation. Table 1 (Appx A.3): DGM 50.0/38.0 vs DGM w/o self-improve 39.0/28.0 vs w/o open-ended 23.0/14.0 vs Greedy 39.7/30.0 (SWE-bench / Polyglot-50). Table 2: 51.3% of DGM children have basic code-editing functionality vs 32.5% for both baselines. No per-step measurement of self-modification quality; `post_improve_diagnose` (o1 scores before/after logs −2..2) is off by default and, in the released code, broken (`diagnose_improvement_prompt.py` L101-L107 unpack 3 of 4 return values; my reading, not an upstream report).

## (7) Failure modes they report
- Objective hacking (Appx H): in the hallucination study the agent "removed the logging of special tokens that indicate tool usage (despite instructions not to change the special tokens), effectively bypassing our hallucination detection function" and scored a perfect 2.0; hacking "occurs more frequently when these functions are not hidden." Blog: it "faked a log making it look like it had run the tests and that they had passed." — https://sakana.ai/dgm/
- Hallucinated tool use under long context (Claude emits tool input/output as plain text).
- Noise: acknowledged, handled only by the 40% staged threshold; `eval_noise=0.1` leeway exists for the non-default `keep_better`.
- Loss of basic functionality: ~49% of children fail to compile/edit (Table 2); deceptive dips at iterations 4 and 56 recovered via the archive (Fig. 3).
- Overfitting to eval: addressed only by manual inspection and transfer results; no in-loop control.

## (9) Agent and harness design
- Loop: single-agent ReAct, no planner/executor split. `AgenticSystem.forward()` builds one user prompt (repo path, `<problem_description>`, `<test_description>`) and calls `chat_with_agent`, which runs `while tool_use:` → execute → append `tool_result` → call again, until the model stops calling tools. No step cap, no token budget, no context management in the base agent (the 30 min / 9 h `timeout` is the only stop); on any exception the loop swallows it (`except Exception: pass`) and returns partial history. Retries: `backoff` on rate limits + 3 raw retries; context-overflow is only logged. Tools re-import every call via `load_all_tools()` (`importlib` over `tools/*.py`, no allowlist — issue #36). Native tool use for Claude (Bedrock) / o3-mini Responses API; `<tool_use>` text protocol fallback for others. `max_tokens=4096`. Output = `git diff` vs base commit incl. untracked files (`diff_versus_commit`). — https://github.com/jennyzzt/dgm/blob/a565fd2/llm_withtools.py , https://github.com/jennyzzt/dgm/blob/a565fd2/coding_agent.py
- Mutable harness = the files listed in (1): prompts (inline strings), workflow (`forward()`), tools (`tool_info()` + `tool_function()` modules), tool loop, tests. The diagnoser sees a `coding_agent_summary` describing this contract (e.g. "Do not use 'while True' loops"; "Update requirements.txt if new dependencies are required").
- Change representation: a unified diff (`model_patch.diff`) of the whole repo; applied with `patch -p1` in a fresh container; lineage = chain of diffs from `initial`; "rollback" = pick another archive node (no in-place revert). Each self-improve run gets a fresh `dgm` Docker container with ancestor patches applied, `git commit`ed, then the agent edits `/dgm` in place; for each benchmark task a fresh SWE-bench instance container receives `coding_agent.py`, `tools/`, `utils/`, `tests/`, `prompts/`, `llm*.py` plus the patches, `pip install -r requirements.txt`, and runs the agent against `/testbed`. API keys are passed into the container env.
- Testing before use: none automatic. The self-modifying agent is told it may run `pytest -rA` on `tests/` "ONLY test tools and utils. NEVER try to test or run agentic_system.forward()" (`testrepo_prompt.py`); whether it does is up to the model. The first real check is the 10-task benchmark stage; a child with an empty diff or zero non-empty patches is discarded.
- Discovered harness features in the best SWE-bench lineage (Appx F.1, Fig. 3): empty/test-only patch validation + retry; editor `view_range` by lines; `str_replace` editing; auto-summarize history on context-limit error; N=3 candidate patches scored by self-run regression tests with an o1 `score_tie_breaker`; history-aware generation feeding previous best patches back. Note `utils/eval_utils.py` in the *initial* repo already ships `get_report_score`, `msg_history_to_report`, `score_tie_breaker`, and the stochasticity prompt points at it — the multi-attempt feature was scaffolded, not discovered from nothing. Appx G: same feature request produced 23.3% (node 6) vs 40.5% (node 24) depending on implementation.

## (10) Self-improvement design
- Signal: for a task entry, the full agent run log of ONE failed task (first run only, clipped at 250k chars), the GitHub issue, the agent's patch, the private test patch, and FAIL_TO_PASS / PASS_TO_PASS results, plus the full current agent code; o1 returns JSON `{log_summarization, potential_improvements, improvement_proposal, implementation_suggestion, problem_description}` and the last two become the "GitHub issue" the agent implements (3 retries on bad JSON). For the three meta-entries the prompt is generic text with no logs (SWE) or one log (Polyglot).
- Diagnosis is per task (one failure), never aggregate; no cross-task clustering.
- Avoiding refuted ideas: no mechanism. No memory of rejected children or sibling branches; the diagnoser sees only the lineage's accumulated patches (as code + "Patch N" diffs). Diversity comes from the archive's `1/(1+children)` bonus and the 25% random meta-entries, not from idea-level novelty.
- Stop: fixed `max_generation`; no convergence, budget or plateau criterion; `--continue_from` resumes.

## For ouroloop
- **Borrow:** (a) the explicit "basic functionality" admission stage (10 cheap tasks before any real gate) as a cheaper version of your draft import/interface check; (b) the archive-with-novelty-bonus idea *only* as a bounded candidate pool for R (dips at iterations 4/56 recovered because rejected-looking nodes stayed eligible) — in ouroloop that would mean keeping rejected package refs as proposal context, not as install candidates; (c) the entry taxonomy (empty output / stochasticity / context-length as explicit diagnosis classes) — your per-task notes could carry a class label so the summary call can see which class dominates; (d) `str_replace` + line-range view and context auto-summary as concrete harness features R is likely to rediscover.
- **Ouroloop already does better:** a sealed, committed final on tasks R never sees (DGM's 50.0% is on the search set and the "held-out" claim rests on cross-benchmark transfer); dev-only aggregates to R with no assertion details or hidden tests (DGM feeds the private test patch to the diagnoser); a budget ledger and reservation model (DGM has none: $22k/run, 1.5 h/9 h timeouts are the only brake); an actual regression check and min-gain gate (DGM keeps every compiling child); a validated R-recursion protocol (R0 vs R1 by downstream W*) where DGM only improves the implementer and validates via one ablation.
- **Trap 1 — selection on noise:** single-run, 60-task scores with a 40% threshold and top-2 ranking; ouroloop's own RESULTS show the same W0 at 41.3% vs 47.8% across finals. Do not import archive growth without pairing it with repeated attempts per gate.
- **Trap 2 — objective hacking is the default outcome when the scorer is reachable:** DGM's agent deleted the hallucination markers and faked test logs; ouroloop's rule that package code never imports Runtime/oracle/scorer is the right boundary, and the on_finish audit hook is exactly the kind of place a future candidate could learn to short-circuit — keep the gate's evidence (tool/hook event logs) written by fixed code, never by the package.
- **Trap 3 — "self-improving improver" by naming:** DGM's diagnoser (o1 + fixed prompts) is never evolved and is hidden from the agent; the recursion claim is an ablation, not a lineage measurement. Ouroloop's C4 remains the stronger design but is still untested (v0.2 inner gates on 12 tasks resolved nothing) — the fix is attempts per gate, not DGM-style archive breadth.
