## 0. One-paragraph summary

AutoSaddler (Microsoft + POSTECH/KAIST, arXiv 2026-08-24, NeurIPS 2026 poster) treats an agent's harness as code and runs an offline mini-batch loop: sample 3 training tasks, run the current harness, let a Claude-Agent-SDK session read the failure traces plus the harness source and apply one patch to allow-listed files, re-run the same 3 tasks, accept if the mean strictly improves, and only then run the full dev split; a separate reflection session writes "lessons" and an evolution session picks (and may recombine) which accepted ancestor the next iteration starts from. The final harness is the argmax over dev among accepted candidates, evaluated once (3 repeats) on a group-disjoint test split. Reported: GAIA2 53.0 → 62.0, SWE-Bench Pro 37.3 → 46.9, Terminal-Bench 2.0 40.0 → 50.0 Pass@1, all with Claude Opus 4.6 as optimizer and executor ([paper](https://arxiv.org/abs/2608.23041), [README](https://github.com/microsoft/AutoSaddler/blob/main/README.md)). It does not improve its own improver and explicitly says so.

## 1. What it modifies

- Formal space: θ = (θ_prompt, θ_tool, θ_middleware): system/instruction prompts, tool definitions and implementations, and "runtime control logic, including hooks and agent-loop behavior". Memory and skill curation are explicitly out of scope ("our setting assumes tasks are largely stateless and independent"); model weights are never touched ([paper §3, lines 186-194](https://arxiv.org/html/2608.23041v1); `optimizer-invariants.md`: "It does not train model weights").
- Nine patch subtypes in two groups (paper Table 1): Steering (text only: prompt rule add/modify, tool-description fix, PreToolUse hook reminder) vs Capability (code: new tool, argument modification, implementation fix, infrastructure change such as iteration budget/config, agent-loop logic change).
- Concretely for GAIA2 the v2 config allow-lists 5 paths — `are/simulation/agents/default_agent` (prompts, base agent loop, action executor, termination), `are_simulation_agent_config.py`, `agent_config_builder.py`, `apps/agent_user_interface.py`, `hook.json` — and forbids 10 (validation, scenarios, benchmark, tests, data, checkpoint, gui...) ([configs/v2/meta_are_full.yaml](https://github.com/microsoft/AutoSaddler/blob/main/configs/v2/meta_are_full.yaml) lines 19-35). The v1 paper-era allow-list was broader: ~26 files including every app's tool module (`apps/email_client.py`, `cab.py`, `contacts.py`, ...) ([v1 CLAUDE.md](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v1/proposer/autosaddler/CLAUDE.md) "Editable paths"), which is how the paper's new tools (`search_ride_history`, `get_crime_rates_batch`, `search_contacts` field expansion) were possible (paper Table 16).
- Not modified: the optimizer's own prompts/skills (see §5), the evaluator, the judge, the benchmark data.

## 2. The improvement loop

Per iteration n (v2 `engine.py::_run_iteration`, lines 214-500; paper Algorithm 1, lines 1001-1017):

1. Sample mini-batch B_n ⊂ D_train. Policy `epoch_shuffled`, `batch_size: 3`, seeded shuffle per epoch, no replacement within an epoch ([policies.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/core/policies.py) lines 38-101; v1 `train_minibatch_size: 3` in [configs/v1/meta_are.yaml](https://github.com/microsoft/AutoSaddler/blob/main/configs/v1/meta_are.yaml)). Paper Appendix I says "six training scenarios per optimization iteration", which I read as 3 cases × (before + after) rollouts — inference, not stated.
2. Evolution session (v1 "Session 0", skipped on iteration 1): an LLM session reads the full history and returns `parent_ids` (first = base) plus optional `component_sources` (whole-file replacements from other accepted parents). Only accepted candidates are selectable; declined/rejected ones never are ([engine.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/core/engine.py) lines 238-278, 1274-1304). In v1 the agent itself did `rsync`/diff-level cherry-picks/reverts in the worktree, recorded by `evo-dag update-selection` (paper Fig. 15).
3. Evaluate the parent on B_n (`train_before`). If every observation succeeded the iteration ends with outcome `no_training_failures` and no session is spent (engine lines 286-298).
4. Diagnosis-Patch session: one session, one child. Inputs: staged `training_evidence.json` (per case, per repetition: disposition, score, judge rationale, full interaction trace, token usage) + the harness workspace + history bundle. Output schema: `intent`, `diagnosis`, `expected_effect`, `changed_paths` ([prompt_pack.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/prompt_pack.py) lines 544-562). Engine checks declared `changed_paths` == observed workspace delta or rejects (engine 1315-1325).
5. Verify and finalize (see §9), evaluate the child on the same B_n (`train_after`).
6. Acceptance: `MatchedValidStrictImprovement` — mean score over matched valid (case, repetition) pairs, child > parent, strictly (policies 104-139). v1: "A patch is accepted if the sum of re-evaluation scores exceeds the sum of initial scores. Even fixing a single scenario is enough" (v1 session1 prompt line 397-399).
7. Dev gate `full_on_accept`: accepted children are evaluated on the whole dev split; declined ones are not (policies 148-156).
8. Reflection is deferred to the start of the next iteration (so the dev score exists); it returns `lessons[]` with `scope`, `statement`, `evidence_case_ids` (train IDs only, validated) and the engine stores them as `ExtensionStateChanged` events (engine 596-685).
9. Repeat until `max_iterations` or `max_rollouts` (counted as `EvaluationAttemptStarted` events) is hit; then `BestCandidateSelected`.

Candidates per iteration: exactly one (plus an optional composed parent). Iterations in the paper: 2 epochs on GAIA2 and SBP, 4 on TB2; with 75 train / batch 3 that is 50 iterations on GAIA2 (Appendix B "Optimization Budgets", lines 1220-1229; Fig. 6 shows Iter0–Iter47). Phased schedule: capability patches for the first k = E·|D_train|/B iterations with E = 1 (25 on GAIA2), then steering only (paper lines 1068-1084; v2 `capability_phase_iterations: 25`). Archive: the EvoDAG — every candidate is a node (status proposed/declined/accepted/selected), edges carry the diff, nodes carry train-before/after, dev score, intent, verdict, reflections; v1 also kept a per-scenario registry (`known_root_causes`, `attempted_fixes`, `sensitive_to_files`, category such as `volatile`/`consistently_failing`) ([lesson_manager.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v1/proposer/autosaddler/lesson_manager.py) lines 481-611). GAIA2 run: 51 candidates total, 21 accepted and dev-evaluated (Appendix J); Table 13 counts 39 generated / 19 rejected / 20 accepted patches.

## 3. Evaluation and selection

| Item | Value | Source |
|---|---|---|
| Acceptance split | the same 3-task mini-batch, 1 repetition (`repetitions: 1`, v1 `num_runs: 1`) | configs; policies.py |
| Acceptance rule | strict `after > before` on matched valid observations; no margin, no significance | policies.py 104-139 |
| Regression check | none as a gate. Regressions are classified (`fixed/regressed/still_failing/still_passing`), recorded as bad patterns, and left to the Reflection/Evolution agents to revert | v1 CLAUDE.md "Acceptance Criteria"; paper Fig. 4 |
| Dev split | GAIA2 65 tasks (Universe 30), SBP 80 (Vuls 40 + NodeBB 40), TB2 19; evaluated once per accepted candidate | paper Table 6; `full_on_accept` |
| Final selection | argmax of mean dev score among accepted, dev-evaluated candidates (ties → earlier) | `MeanDevelopmentRanking`; paper eq. θ̂_AS |
| Held-out final | test split evaluated once after the run, 3 repeated executions, mean ± SD; "not further modified using test feedback" | paper lines 276-277, 434-436 |
| Statistics | no hypothesis tests or CIs; single optimization run per method (one extra run in Appendix C) | paper Appendix C |

Note the dev set is used for selection, so dev numbers are optimistic: the GAIA2 run peaked at 72.3% dev (Iter27) and the same harness scored 62.0% on test (paper Fig. 6 and Table 2).

## 4. Leakage controls

- Splits are by task group: GAIA2 by Universe (train U29, dev U30, test U21/22/27), SBP by repository/language, TB2 random because there is no grouping axis (Table 6). Test payloads are never opened by the engine; the manifest is only hashed (`"test": {"state": "opaque_to_optimizer", "payloads_opened": False}` in [plugin.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/plugin.py) lines 390-396).
- Dev: the optimizer sees only the aggregate dev score. Code enforcement: the evidence builder raises on non-train evaluations ([evidence.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/evidence.py) line 176), dev artifacts go to `quarantine/dev/` (engine 1085-1089), `capture_traces=split == "train"` (engine 1097), reflection lessons may cite train IDs only (engine 1364-1379). Prompt enforcement in v1: "Do NOT read raw traces from development set dirs" (session2 prompt lines 816-819).
- Anti-cheating verifier: any changed `.py/.json/.md/.toml/.yaml` file containing a training case ID string is rejected ([verification.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/verification.py) lines 55-68); prompts forbid "task-specific names, IDs, answers, or lookup tables".
- What the proposer does see for train tasks: the judge's rationale and, in v1, "oracle expectations" (diagnose skill step 4: "Compare what the agent did against what it should have done (from the evaluation rationale and oracle expectations)"; the paper's case studies "cross-verify this with the oracle events", lines 1672-1673, 1686-1687). So gold trajectories of train tasks are visible to the patcher; the only defences against encoding them are the ID-substring check, prompt rules, and the dev gate. v2 SYSTEM.md tightens this: "Do not infer oracle actions or hidden scenario state that the evidence does not show."

## 5. Is the improver improved?

No. The three optimizer agents run fixed prompts and skills (paper Appendix P, Figs. 13-15); in v2 every prompt/skill asset is hashed into `resolved/prompts/compositions.json` and a changed asset makes resume fail, i.e. the improver is frozen per run ([prompt_pack.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/prompt_pack.py) lines 678-709, 734-757). The paper disclaims self-referentiality: "we do not impose such constraints, as our objective is to improve the task agent's external harness under a finite rollout budget rather than to model self-referential dynamics" (lines 136-139). The only cross-iteration learning in the improver is data: the EvoDAG lessons, scenario registry and diffs that later sessions read. The follow-up ActiveSaddler (arXiv 2610.00906, 2026-10-01, same group) adapts which training tasks are selected via a non-stationary bandit, reporting +4.4 (GAIA2) and +7.5 (TB2) Pass@1 over fixed ordering ([abstract](https://arxiv.org/abs/2610.00906); numbers taken from the abstract page only, not verified further) — still not an improver that edits its own prompts. No validation of any improver change exists because none is made.

## 6. Reported results

Models: Claude Opus 4.6 as optimizer (Claude Agent SDK, `effort: max`, `bypassPermissions`) and as task agent for all methods; judge for GAIA2 is Llama-3.3-70B-Instruct per the GAIA2 protocol (paper lines 416-437, 1163-1166). The checked-in v2 configs differ: the smoke config runs the task agent and judge on `gpt-4.1-mini` with a `claude-opus-4-6` optimizer, and `meta_are_full.yaml` uses `gpt-5.5` via the Copilot provider for both roles — so the shipped v2 configs do not reproduce the paper setup ([README "Reproducing"](https://github.com/microsoft/AutoSaddler/blob/main/README.md); configs/v2).

Ablations on GAIA2 (Table 2, Appendix F): w/o in-depth diagnosis 57.8; w/o structured intervention 56.9 (w/o phase scheduling alone 54.8 on U22); w/o generalization-aware selection 50.6 (w/o dev-set filtering alone 50.0 on U22, additionally w/o reflection+EvoDAG 44.9). ## 7. Failure modes they report

- Over-scoped steering on high-frequency tools: a hook on `add_calendar_event` firing on every call (Iter 4, blocked by reflection); the ablation's `send_message_to_user` redirect hook at Iter 20 raised the dev regression rate 8% → 22% and dropped dev to 33.8% (paper lines 617-626, Fig. 6, Appendix M).
- Steering patches regress twice as often as capability patches (17% vs 8%) at similar fix rates (58% vs 55%) (Appendix G, Tables 11-12).
- Accumulation: Iter 46 cherry-picked 8 hooks/rules and lost 12.3 pp; Iter 47 pruned to 4 (Appendix J). Prompts therefore say "prefer replacement over addition".
- Over-correction from prohibitive phrasing ("Do not add pleasantries" stripped content evaluators expected; replaced by a constructive template at Iter 27) (Table 16, Fig. 12c).
- Silent misconfiguration: a hook matcher `EmailClientV2_reply_to_email` never matched the real tool name, "zero hook feedback messages appear in the trace" (Fig. 12c, Iter 8).
- Noise: the reflection prompt mandates a "stochasticity check" because "the same agent code can produce different tool-call sequences across runs"; the evolution prompt says "Dev scores are noisy" (Appendix P). The paper gives no estimate of the noise floor of the 3-task acceptance gate.
- Without the taxonomy/phases the proposer collapses onto steering edits (91.5% of patches) (Fig. 3).
- Reward hacking: not observed/reported by them; GAIA2's judge has a `sanity_checker` for garbled output (v1 CLAUDE.md), and the ID-substring check is their only patch-level guard.
- Limitations (Appendix R): requires gold labels and a task-level metric; stateless tasks only; no memory/skill curation; "automated harness modifications should undergo human review or additional security validation before deployment".

## 9. Agent and harness design

**9a. The agent being optimized (Meta-ARE default ReAct JSON agent).** Loop in [base_agent.py](https://github.com/pshlego/Meta-ARE/blob/395d1dd512add1e3aeb5a6a092490768b51e3ce5/are/simulation/agents/default_agent/base_agent.py) `execute_agent_loop` (lines 873-953): while termination condition false → pre-steps (pull user messages and environment notifications into the log, `steps/are_simulation.py`) → `step()` → post-steps. `step()` (613-780): rebuild the whole message history from the typed log list (`build_history_from_logs`, 442-540; roles plan/facts/observation/error/environment_notifications), call the LLM with stop sequences `<end_action>`/`Observation:`, retry while the output lacks Thought/Action tokens up to `invalid_format_retries`, parse exactly one JSON `{"action","action_input"}` (`json_action_executor.py`), run the PreToolUse hook middleware, execute the tool, append the observation. Context management: on `PromptTooLongException` the previous observation is dropped and replaced by its first/last 100 chars (474-489); tool errors are fed back as "Now let's retry: take care not to repeat previous errors!" (110). Stop: tool call `AgentUserInterface__send_message_to_user` or `SystemApp__wait_for_notification`, an environment stop message, or `max_iterations` (80 by default; a `MaxIterationsAgentError` is logged and "Max iterations reached" is sent to the user) ([termination_methods/are_simulation.py](https://github.com/pshlego/Meta-ARE/blob/395d1dd512add1e3aeb5a6a092490768b51e3ce5/are/simulation/agents/default_agent/termination_methods/are_simulation.py) lines 80-115; `are_simulation_agent_config.py` line 36). No planner/executor split in the default agent (plan/facts prompts exist in `additional_prompts.py` but are optional); no cross-episode memory. Middleware: `hook.json` is loaded by `scenario_runner.py` (lines 265-278) into `HookMiddleware`; a `reminder` handler denies the first call to a matched tool and injects the reminder text as a `[HOOK FEEDBACK ... BLOCKED]` hint, then auto-allows (fire once per tool name); `prompt` and `agent` handlers call the agent's LLM or a GC-SDK session to return allow/deny; deny beats allow; handler errors default to allow ([hooks/middleware.py](https://github.com/pshlego/Meta-ARE/blob/395d1dd512add1e3aeb5a6a092490768b51e3ce5/are/simulation/agents/hooks/middleware.py) lines 34-160). The pinned base `hook.json` is `{"hooks": {"PreToolUse": []}}`.

**9b. The optimizer agents.** Three session kinds (`evolve`, `diagnose_patch`, `reflect`) run through a provider (Claude Agent SDK, GitHub Copilot SDK, Codex CLI, or fake). A `SessionSpec` = system context (core `optimizer-invariants.md` + plugin `SYSTEM.md`), task prompt (core `*-method.md` + plugin prompt), skills, a JSON Schema output contract, staged workspace files, and required capabilities; the renderer writes `CLAUDE.md`, `.claude/skills/<name>/SKILL.md`, `.autosaddler/session_output_schema.json`, and the agent must write `.autosaddler/session_output.json`, which the engine validates with jsonschema ([workspace_renderer.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/providers/workspace_renderer.py); [prompting/models.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/prompting/models.py) 957-970). Capabilities map to tools: read_workspace → Read/Glob/Grep, edit_workspace → Edit/Write, run_commands → Bash, load_skills → Skill ([workspace_renderer.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/providers/workspace_renderer.py) 831-839). Claude provider defaults: `claude-opus-4.6`, `effort: max`, `permission_mode: bypassPermissions`, `setting_sources: ["project"]` ([providers/claude.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/providers/claude.py) 377-415). Timeouts: diagnosis 18,000 s, selection 1,800 s, reflection 3,600 s; `session_retries: 2` with exponential backoff; exhausted evolve retries fail the run, exhausted diagnosis retries record a no-proposal iteration, exhausted reflection retries abandon that reflection ([v2-architecture.md](https://github.com/microsoft/AutoSaddler/blob/main/docs/v2-architecture.md)). The history the agent reads is a generated bundle under `.autosaddler/history/` (manifest with sha256 of every file, `summary.json`, `lessons.json`, `current_batch.json` with per-case prior iterations, per-candidate JSON, per-edge JSON, full diffs) built from the event log at each session ([history.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/prompting/history.py)); v1 exposed the same through an `evo-dag` CLI with `summary / show history / show node / show edge / show scenario / show lessons / update-selection / update-intent / update-reflection` (paper Table 5).

**9c. What a "harness" is in code and what is mutable.** Two candidate spaces: `ComponentMapHarnessSpace` (a frozen-key map of named text components; mutations are a JSON `updates` object) and `GitHarnessSpace` (a commit-pinned repo; mutations are file edits inside `writable_paths` minus `forbidden_paths`) ([harness/git.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/harness/git.py), [component_map.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/harness/component_map.py)). Phase scoping: in steering phase the verifier rejects any changed `.py`, so for Meta-ARE (whose prompts live in Python) steering is effectively `hook.json` only; SYSTEM.md states this ([verification.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/verification.py) 49-53; [SYSTEM.md](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/SYSTEM.md) "Mutation Phases").

**9d. Change representation, application, versioning.** The agent edits a copy of the parent worktree (provider assets and `.git` excluded). The engine captures a `WorkspaceDelta` (full base64 content + exec bit of every changed path, canonical JSON, sha256-named under `mutation-deltas/`), replays it onto the detached worktree, runs the verifier, commits as "AutoSaddler candidate <id>", and publishes the child with `candidate_id = sha256(git ls-tree -r --full-tree)` (tree identity, path-independent), a `change.patch` (`git diff --binary`), and a `ChangeSummary` (changed_units, +/- lines, labels = phase) ([git.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/harness/git.py) 120-287, 442-483). Composition = whole-file replacement from other accepted parents, re-verified and committed as its own candidate (289-351). Lineage lives in the append-only `events.jsonl` (`CandidateFinalized`, `AcceptanceDecided`, `DevelopmentGateDecided`, `EvolutionRecorded`, `MutationRejected`, `BudgetUpdated`...), from which `RunState` is replayed; `evolution_dag.json` and `manifest.json` are projections. Rollback is not an engine operation: it is the evolution session choosing an earlier accepted node as base (Fig. 6 "rebase to Iter13"). Resume requires byte-identical resolved inputs; fork allows only `max_iterations` to differ ([v2-architecture.md](https://github.com/microsoft/AutoSaddler/blob/main/docs/v2-architecture.md)).

**9e. Isolation and testing before use.** Isolation of the candidate: separate `git worktree` per candidate, symlinks rejected, provider assets excluded from identity, forbidden-path and allow-list checks at delta application and at finalize. Isolation of the optimizer agent: none beyond workspace conventions — it runs with Bash and `bypassPermissions` on the host; the README tells you to run from an external `working_dir` so "generated workspaces cannot inherit repository-level agent instructions through Git ancestry". Tests before use: `compile()` of each changed `.py`, `hook.json` structure + `re.compile` of matchers + handler type/text checks, steering-scope check, train-ID anti-cheating scan, and an import smoke test `from are.simulation.agents.default_agent import base_agent` via `uv run --project <workspace>` with a 300 s timeout ([verification.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/verification.py)). No unit tests of the patched behaviour; the behavioural test is the re-run on the mini-batch. Task execution: the benchmark CLI runs as a subprocess in the materialized worktree with `--scenario_timeout 1800`, `--max_concurrent_scenarios 3`, HF forced offline, one infrastructure retry, per-attempt `command.json`/`completion.json` for idempotent resume ([runner.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/runner.py)); GAIA2 apps are in-process simulations (no container), while SBP/TB2 in the paper used per-instance Docker/Harbor (Appendix B).

## 10. Self-improvement design

- Signal: per-case failure traces (every tool call, response, reasoning step), the judge rationale and score, success traces too ("both successful and failed runs"), repetition consistency (`consistent_pass / consistent_failure / intermittent`), the harness source, and the history bundle. After the patch: per-case before/after scores classified into fixed/regressed/still_failing/still_passing, plus the aggregate dev score when accepted ([evidence.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/plugins/meta_are/evidence.py); engine 461-493).
- Diagnosis granularity: per task ("For each failing scenario, use the diagnose skill... the first point where those paths diverged... the candidate surface that controlled the observed decision"), then one patch that may target several cases; reflection per case with a mandatory causal attribution ("TRUE FIX / TRUE REGRESSION / STOCHASTIC" with the divergence step and whether the diff touches that code path); lessons aggregate across iterations and, per the paper, mature from atomic to pattern-level to principle-level (Appendix M, Fig. 12c) ([causal-diagnosis/SKILL.md](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v2/prompting/methodology/skills/causal-diagnosis/SKILL.md); paper Fig. 14).
- Avoiding refuted ideas: prompt-enforced only. `history-analysis` is the mandatory first step of every session; the diagnosis must be "distinct: does not repeat a failed prior explanation without new evidence"; v1 kept a scenario registry of `attempted_fixes` with `failure_reason` and `prevention_or_next`, `known_root_causes` (capped at 10), and `sensitive_to_files`, and auto-derived `good_patterns`/`bad_patterns` from fixed/regressed/still_failing reflections ([lesson_manager.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v1/proposer/autosaddler/lesson_manager.py) 392-430). There is no automated novelty or duplicate-proposal check in code.
- Stopping: budget only. v2 `BudgetPolicy(max_rollouts, max_iterations)`; v1 composite stoppers (`MaxMetricCallsStopper` 3000, `MaxCandidateProposalsStopper` 200, timeout, `NoImprovementStopper`, score threshold, signal/file) ([stop_condition.py](https://github.com/microsoft/AutoSaddler/blob/main/src/autosaddler/v1/utils/stop_condition.py); configs/v1). The paper runs a fixed epoch count and returns the dev argmax; no convergence test.

## What ouroloop should take from this

- **Borrow: engine-owned experiment memory with causal attribution.** AutoSaddler's biggest measured component is generalization-aware selection (62.0 → 50.6 without it; dev filtering is the larger half, reflection+EvoDAG adds 5.1 pp). The reusable part is the shape of the memory: a fixed, engine-generated history bundle (per-case prior attempts, per-candidate diffs, lessons with scope + evidence IDs + a TRUE/STOCHASTIC label) that R reads first every round, and a reflection step that runs after the gate. ouroloop's v0.2 R1 ("say what each rejection rules out, never re-propose a refuted mechanism") is the same idea but lives in R's prompt; making the ledger an M7/K artifact that any R0/R1 consumes would also make the C4 comparison cleaner.
- **Borrow: capability-first phasing and the regression evidence behind it.** Steering text regresses twice as often (17% vs 8%) and an unconstrained proposer spends 91.5% of patches on text. Both of ouroloop's installed changes so far are text (pre-write protocol, on_finish audit) while DESIGN.md §7 requires at least one real tool/hook behaviour change; a short capability-only segment (tool wrappers / middleware code in the package) before text refinement is a cheap, pre-registered way to force that, and the compile + import + "declared changed_paths == actual diff" verifier is directly portable to M4's draft check.
- **Borrow: DAG, not chain.** Letting R choose an earlier accepted package as the base (and compose whole files from another accepted package) is what rescued AutoSaddler at Iter 20 and Iter 46; ouroloop always chains from the active W. Since packages are already content-addressed in the object store, a schema-constrained `parent_ids` choice in `research.propose` is a small addition.
- **Already better in ouroloop: the gate and the final.** AutoSaddler accepts on a strict `>` over 3 tasks × 1 run (one flipped task = +33 points) and uses dev only to rank, never to block; its final is a dev-selected argmax with mean ± SD over 3 reruns and no interval or sealed plan, from a single optimization run. ouroloop's full-dev paired gate with `min_gain` and regression tolerance, the pre-committed final with bootstrap intervals, the per-call reservation ledger (AutoSaddler only counts rollouts; `Cost.currency_amount` is optional and unenforced), and the R0/R1 recursion (which AutoSaddler explicitly does not attempt) are all ahead. Also note their own dev-to-test gap (72.3 → 62.0) mirrors ouroloop's 80–84 → 52.
- **Trap: importing the proposer's freedom without its guards, and the guards without their cost.** AutoSaddler's optimizer edits a repo with Bash and `bypassPermissions`, sees judge rationales and oracle events for train tasks, and relies on a case-ID substring scan plus prompt rules to stop answer-encoding; ouroloop's Docker worker, package-only mutation surface, and train-only assertion detail are the stricter boundary and should not be traded for speed. Conversely their loop needs ~50 iterations, ~1,000 rollouts (551k input tokens each) and $14.56 of optimizer spend per patch to reach its peak, and small text patches silently accumulate (Iter 46, −12.3 pp); ouroloop's 3-round segments and "merge/disable duplicate components" rule are the right scale for a $300 activity, but the inner research-slot gates (12 tasks, one task = 8 points) share AutoSaddler's noise problem and need repeats, not a looser acceptance rule.
