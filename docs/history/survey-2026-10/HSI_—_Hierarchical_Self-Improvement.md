## 2. The improvement loop

Per `GodelAgent.evolve()` (https://github.com/TailinZhou/hsi/blob/main/src/react_loop/agent.py) and `EvolveHelper.run_iteration()` (https://github.com/TailinZhou/hsi/blob/main/src/react_loop/evolve.py), each of **T = 5** outer iterations is:

1. Fold in staged meta-evolver edits.
2. **Seed selection**: a react loop (≤ 50 steps, scope `pick_seed`, tools `read_file/bash/evaluate` + `pick_seed`, `pick_seed_ensemble`, `checkout_version`, `view_node`) reads a candidate table of all committed versions, a lineage tree and LLM-written "correlation" edges from the knowledge graph, and the `## Lesson` block of `BOOTSTRAP.md`; it must "inspect 2+ candidates" and emit a hypothesis with rationale, expected improvement, falsification criterion, plus "2-4 competing hypotheses". It may fuse versions (`pick_seed_ensemble` spawns an `atom` sub-agent that merges code) and may spend up to 2–3 `evaluate` calls on a fresh fusion. Short-circuits with 0 or 1 candidates.
3. **INIT commit** carrying the seed hypothesis.
4. **Main evolution**: one react loop, ≤ 80 steps (one LLM call = one step), the agent edits files, calls `evaluate` (prompt says "a healthy iteration runs 2–5 evaluate calls; past 7 is debugger territory"), writes `plan`, bookmarks promising versions with `pick_commit_version(code_hash)`, and ends with `lesson` + `compact_context` (or `end_evolution`). Max steps forces a 3-step wrap-up.
5. **Commit selection**: the same conversation is continued with the nudge prompt; the agent calls `finalize_commit_pool` with **2–5 versions** "spanning different directions"; each becomes a squashed commit on top of the parent, a tag, a tracker record and a knowledge-graph node. Fallback if it doesn't finalize: last bookmark, else the version with the best single-eval reward.
6. **Meta-evolution** (≤ 50 steps, skipped after the final iteration): edits `evolution/`, must run `validate_archive`, then `end_meta_evolution`.

After T: **best-version selection** (`submit_best`, ≤ 80 steps, fixed strategy) picks the export, then the test evaluation runs from the exported directory.

- Candidates per iteration **K_t is not fixed**; the paper says "M determines when to inspect code, propose changes, evaluate candidates, and terminate an iteration" (§3.3.2). In code every `evaluate` call snapshots a `code_hash` and those are the candidates.
- **Archive**: one evolving lineage ("Not test-time search. One candidate per iteration; no population-based parallel scaling. Population-level diversity is preserved via the commit pool", README), with a git-backed archive of all pool commits and a knowledge graph (`knowledge_graph.py`: backbone edges = git parent/child; semantic edges = one LLM diff analysis per node pair).

## 3. Evaluation and selection

- **Reward**: per task, LCB over episodes `r = μ − z·σ/√n`, z = 0.5, then averaged over tasks (`state.lower_confidence_bound`, `balrog/evaluator.py`). With dev episodes = 1 (MiniHack, NLE, all BabaIsAI) the LCB collapses to the raw mean, so the "instability penalty" is only active where dev episodes = 3 **[inferred from code + Table 3]**.
- **Splits** (`benchmark/adapter.py`, `_load_and_split_tasks`): Setup A `dev_ratio 1.0, val_ratio 0` → dev = all tasks, no val, no held-out tasks; "test" = the same tasks under deterministic seeds. Setup B `dev_ratio 0.8` then val carved from dev (`val_ratio` 0.20 BreakStop, 0.25 GoTo/Make). Sub-suite sizes from `balrog/tasks.py`: GoTo 11, BreakStop 10, Make 16 tasks → **[inferred from code]** test = 3 / 2 / 4 tasks, val = 2 / 2 / 3, dev = 6 / 6 / 9.
- **Episodes**: dev/val use `num_episodes_dev` (3 for BabyAI/Crafter/TextWorld, 1 elsewhere) with random seeds (PID+time); test uses `num_episodes` (10 BabyAI/TextWorld, 5 others) with deterministic seeds, rotated per repeat; `test_repeats` 3 for Setup A (1 for NLE and all Setup B). Paper Table 3 / Appendix B.1 matches the shipped configs.
- **Task counts for Setup A** (`tasks.py`): BabyAI 5, Crafter 1, TextWorld 3, MiniHack 8, NLE 1. So the Crafter number rests on 1 task × 5 episodes × 3 repeats.
- **Selection**: no statistical threshold, no min-gain gate, no regression check against the previous version. Commit and export are LLM judgments guided by prompt rules ("Val > Dev", "diversity over max reward", "when uncertain default to the single highest-reward candidate"). Mechanical pieces: a **crash veto** (versions whose harness raised are never auto-selected, `EvolutionTracker._get_best_version_val_preferred`), val-preferred ranking, and the rule that a fused version must have been `evaluate`d under its own commit hash before it can be submitted. Dev evaluations return the full dev set each call in the shipped configs (`dynamic_sample: false`), plus an LLM-written per-episode "diary" and per-task analysis; val returns a number only; test is never callable during evolution.
- **Held-out final**: Setup B only. Export is chosen on dev/val; test is run once on the exported directory via a fresh import (`HarnessLoader`, unique package name per load, so "bytes executed == bytes on disk == bytes hashed").

## 4. Leakage controls

- Task-level: in Setup A the proposer saw every task (only seeds differ). In Setup B `evaluate(dev|val)` never returns test tasks (`_get_tasks_for_mode`), and the dev `goal.md` describes the sub-suite generically.
- Code-level: a "benchmark shield" blocks `read_file`/`bash` touching `src/benchmark/` — but only in scopes `meta_evolve, atom, pick_seed, submit_best, probe`; **the evolve scope is exempt** by design ("it legitimately reads task files while solving", `utils/tools.py`). The evolve scope's `read_file` is whitelisted to `repo/`, `eval_logs/`, `src/react_loop/`; `bash` is wrapped in **bubblewrap only when `bwrap` is installed, otherwise run unsandboxed** (`execute_shell`: "silently skipped when not"). So on a host without bwrap the evolver's bash can read the split config and task list. BALROG has no answer keys, so the practical leak is which tasks are test, not solutions.
- Reporting asymmetries: "Init Harness is averaged over three baseline runs" while each evolved arm appears to be a single evolution run **[unverified: the paper never states the number of evolution runs per cell]**; "Best Dev" is a selected maximum; the shipped Setup B configs have `run_all_tasks: true`, so the post-evolution pass evaluates dev+val+test together and how the paper sliced "Best Test" from that output is **not verifiable from the repo**.

## 5. Is the improver improved, and how is that validated?

Yes, by construction: after every iteration except the last the meta-evolver edits `evolution/` (seed prompt + knob block, commit nudge prompt, the evolver's base prompt, strategy modules), with a mandatory **Lesson Audit** that lets it overwrite the evolver's `[Iter N]` lesson lines it judges false, and a `meta_bootstrap` append-only log of its own predictions. Validation of Σ changes is **syntactic/structural only**: `validate_archive` dry-runs `select_seed` with a stub react and checks return formats; on failure `evolution/` is rolled back to the pre-meta commit (`MetaEvolveHelper._reload_modules/_rollback_evo_dir`). There is **no outcome-based test of a Σ change** (no A/B of old vs new evolver on the same seed, no acceptance gate); the next iteration simply runs the new Σ. The only empirical evidence is the paper's end-to-end ablation meta-on vs meta-off (one arm each). The meta-evolver's own code (`meta_evolve.py`, prompts, tools) and `select_best.py` are the "frozen outer anchor" (paper §3.3.4, Appendix A.5). Both the evolver's bash edits to harness code during meta (a "sandbox escape") and edits outside `evolution/` are reverted.

## 7. Failure modes they report

- Two stated bounds: feedback-fidelity (no informative reward → no evolution; NLE flat at 0) and backbone capability (Make stays at 0.36 with ±0.33 across tasks).
- Non-monotonic search: "additional modifications produce regression" (Crafter iteration 5); "the largest performance improvement typically occurs during the first iteration".
- The author on the hardest layer: "the most challenging layer has consistently been the reward signal. Reward instability (noise, sparsity, or non-stationarity) often causes the evolver to make erratic modifications" (https://github.com/TailinZhou/hsi/issues/1).
- Dev overfitting is acknowledged in prompts ("dev-overfit versions masquerading as breakthroughs", "If val ≪ dev, you're overfitting") and the paper cites Wang et al. 2026b on harness evolution overfitting; mitigation is Setup B only.
- "Toxic lessons": the evolver "can make factual errors — it may blame the LLM when the harness was at fault, claim a mechanism works when traces show it was never invoked" (`meta_evolve_prompt.md`); hence the audit.
- Engineering failures fixed in code and pinned by tests: reward stamped onto a stale/broken code hash because of `sys.modules` caching (`tests/test_harness_loader_fresh_import.py`); the probe sub-agent's `git reset --hard` wiping the evolver's uncommitted edits (`tests/test_probe_isolation.py`); the agent's own bash deleting the process CWD (`main.py` comments); crashed harnesses scoring 0 and winning on average (crash veto).
- **Reward hacking is not discussed.** Note a tension: the paper says evolution "cannot replace the model with external search procedures or non-LLM policies", but `evolution_base_prompt.md` explicitly encourages "Hybrid — code + LLM … compute them in workflow() and return without the LLM", and the Make trajectory evolved BFS pathfinding; nothing in the code enforces the paper's constraint.

## 9. Agent and harness design (what the code actually does)

**The react primitive.** `GodelAgent.react(messages, tools, tool_executor, hook_on_request, hook_on_response, hook_on_complete)` is one OpenAI-compatible chat call plus synchronous execution of all returned tool calls; the caller owns the loop and the message list (https://github.com/TailinZhou/hsi/blob/main/src/react_loop/agent.py). Every scope (harness, evolver, seed, commit, meta, submit_best, probe, atom) is this same function with a different system prompt and tool whitelist (`_SCOPE_TOOL_WHITELIST` in `utils/tools.py`). `_call_llm_impl` switches thinking on/off per scope (`extra_body.thinking`), strips `reasoning_content` to keep prompt-cache prefixes stable, and applies `harness_max_tokens` only in harness scope.

**The task harness (W-equivalent).** For BALROG the evaluator calls `using_harness(agent, obs)` once per game step; it imports sibling modules fresh, builds the system prompt (base prompt + the environment's instruction, embedded "so it survives history truncation"), keeps one `HarnessContext` per episode in a thread-local `task_context` (keys: `env_name, instruction, short_term, is_new_episode, last_step_reward, achievements, recent_unlocked`), and calls `HarnessPolicy.workflow()`: `_process_observation → _build_context → _build_message → get_agent_decision (one react) → _postprocess_action → _update_state`. Default = single react, no tools, cliff-truncate history to the last 16 (obs, action) pairs. "Planner/executor" is not built in; the evolver is told the loop itself is the design space (multi-stage react pipelines, state machines, loop/stuck detection, code-only decisions). Hooks are plain functions `(messages, tools) → (messages, tools)`, `(response) → response`, `(response, tool_calls, results) → None`. Stop/finish checks live in the evaluator, not the harness: episode ends on env termination, `max_steps`, or an evaluator-side period-2/3 action-loop detector (`_is_action_loop`). Retries: evaluator-side LLM retries exist only for the auxiliary diary calls; a harness exception marks the episode 0 and the version "crashed".

**The evolver as an agent.** System prompt = fixed `framework_contract.md` + evolvable `evolution_base_prompt.md`; user prompt = goal.md, seed hypothesis, environment/sandbox table, git status, last eval. Tools: `read_file, edit_file, write_file, bash, evaluate(eval_mode, task_ids, num_tasks), plan, lesson, probe, pick_commit_version, compact_context, end_evolution` (`read_history_self`, `get_historic_version`, `view_evolution_graph` excluded by config). Context management: `max_context_tokens 600000`, `max_history_messages 500`, tool results truncated to 100k chars; eval feedback is an LLM-written per-task analysis reusing the episode's own cached message history, plus a `probe` read-only sub-agent (bash+jq over `eval_logs/`) so raw traces never enter the evolver's context. Step 1 gets the prompt; later steps get only tool results with a status suffix (steps left, reward).

**Mutable surface and versioning.** Each `evaluate` computes an MD5 `code_hash` over all `.py` files (excluding `evolution/`), stores the file contents in memory and on disk (`harness_history`), and appends `[code_hash, reward, eval_mode, exec_errors, modified_files, ops]` to `evaluation_snapshots`. Commit = restore snapshot → `git add -A` → `reset --soft parent` → one squashed commit → tag `pool-iterN-k`. Lineage/rollback: INIT commits per iteration, `checkout_version(hash)` for inspection without moving HEAD, seed selection resets `--hard` to the chosen seed while preserving `evolution/`, `.evolution_context/`, `BOOTSTRAP.md`. Meta edits are staged and folded into the next INIT commit; failed meta validation rolls `evolution/` back.

**Isolation and testing of generated code.** Edits via `edit_file/write_file` (and bash-detected disk changes) pass an AST validator (`CodeValidator`: forbids `subprocess`, `multiprocessing`, `socket`, `pickle`, `ctypes`, `os.system/exec/fork`, dunder reflection, `time.sleep`) plus `compile()` for syntax (`agent_action._validate_python_code`). Then the only test is execution: `evaluate` fresh-imports the harness **into the control-plane Python process** and runs episodes in `ThreadPoolExecutor` threads (`balrog/evaluator.py`). There is no subprocess, container or import smoke test before evaluation (the "post-fusion import smoke" exists only in `submit_best`). Bash is bubblewrap-wrapped when available (rw `repo/`, ro `eval_logs/`, ro framework, `evolution/` covered by tmpfs for non-meta scopes, network shared); without bwrap it runs with the host user's rights in `repo/`. The authors' own `main.py` comments record the agent's bash deleting the process CWD mid-run. Framework source `src/react_loop/` is readable by the evolver so it can "read the real framework code it plugs into".

## 10. Self-improvement design

- **Signal**: (a) scalar LCB reward per `evaluate`; (b) per-task failure analyses written by the same model from the episode's message history ("player reports the symptom; engineer attributes" — diaries are told not to name a harness mechanism, to avoid anchoring); (c) raw traces via `probe`; (d) harness crash tracebacks returned verbatim instead of summarized; (e) the seed hypothesis and `BOOTSTRAP.md` lessons. The prompt insists "Reward is too noisy to judge a single edit; the real signal is the failure traces" and "did the failure mode disappear from the failing tasks? That's your verdict", with `task_ids` for deterministic re-runs of named tasks (untracked, so they cannot move selection).
- **Diagnosis granularity**: per task per evaluate (failed-task analyses), aggregated by the agent into one hypothesis per cycle ("one hypothesis per cycle — bundling unrelated changes tells you nothing").
- **Avoiding refuted ideas**: no mechanical novelty check. Three soft mechanisms: `BOOTSTRAP.md` lessons with confidence (injected into seed selection and the evolver, audited and overwritable by the meta-evolver, "overwrite contradicted ones"); the knowledge graph's LLM-written relations (extends / repairs / explores different direction) and lineage tree in the candidate table; seed-selection guardrails ("Don't repeat a dead seed… plateau_window+ flat iterations → you MUST pivot"). The meta-evolver reads per-phase conversation logs to detect "override-happy", "stuck/tweaking forever", "probe spiral" patterns and rewrites the evolver's prompt.
- **Explore/exploit**: deliberately not scheduled by the framework ("Self-determined explore–exploit", paper Principle 2); the commit pool (2–5 diverse versions), ensemble fusion, and the meta-tunable knobs (`plateau_window`, `ensemble_trigger`, `early_phase_fraction`, pool size, inclusion threshold, val gate) are the levers.
- **Stopping**: fixed T = 5 (plus per-stage step caps); the agent may call `end_evolution` early ("Mission Accomplished… reward consistently near-perfect… including val"); meta-evolve never runs after the last iteration; export always happens.

## For ouroloop

- **Borrow**: (1) The *framework/strategy split with a frozen anchor* is the same idea as ouroloop's K vs R, but HSI makes the R-side editable surface richer and still safe: prompt text plus named numeric knobs in a template block the meta-level fills in, validated by a dry-run (`validate_archive`) with automatic rollback. ouroloop's research slot (two prompt bodies) could expose such knobs cheaply. (2) The **commit pool + candidate table + lineage/correlation rendering** gives R a compact, structured memory of what was tried, with hashes it can diff; ouroloop's R1 note "never re-propose a refuted mechanism with more items" is the same need handled as prose. (3) The **lesson audit**: a separate pass that checks each stored lesson against traces and overwrites confident falsehoods — directly relevant since ouroloop's round-1 defect (R misreading clipping marks) was exactly a false lesson. (4) The `code_hash ↔ reward` alignment and crash veto as explicit invariants with regression tests. (5) Dev diaries that describe the symptom without naming the harness culprit, to reduce anchoring in R's notes.
- **ouroloop already does better**: a sealed, committed held-out final with paired bootstrap intervals and an honest noise-floor statement (HSI has no held-out tasks in Setup A, no gate, no CI, single runs, 1–4 test tasks in Setup B); a fixed admission gate with min-gain and regression tolerance instead of LLM judgment; a budget ledger (HSI reports no cost at all); isolated workers for generated code (HSI imports evolved code into the control plane and sandboxes bash only if bwrap happens to exist); and an actual *comparison protocol for R recursion* (R0 vs R1 on the same W/E) where HSI validates Σ changes only syntactically and relies on one meta-on/off ablation.
- **Trap 1 — selection by judgment on noisy dev**: HSI's "Best Dev" and LLM-picked exports are selection-biased by construction and their own author names reward noise as the hardest problem; ouroloop's v0.2 shows the same noise floor (W0 at 41% vs 48% with nothing changed). Do not import HSI's "let the agent decide what counts as better" stance for installs.
- **Trap 2 — meta-evolution without a counterfactual**: HSI's meta-on gains (e.g., TextWorld +19) come from single runs with no paired comparison, so they are indistinguishable from search variance. ouroloop's C4 design is right to insist on the two-arm comparison; the lesson from HSI is only that the research slot needs enough attempts per inner gate, not that the comparison can be dropped.
- **Trap 3 — "harness" absorbing the policy**: HSI's prompt pushes code-only decisions (BFS, state machines) inside the harness, which contradicts the paper's own "cannot replace the model with non-LLM policies" constraint and makes "same-model gain" claims ambiguous. ouroloop's requirement that a candidate show a real tool/hook behavior change is good; add an explicit rule on how much task logic may move into package code before it stops being a harness improvement.
