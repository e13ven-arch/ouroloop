## 5. 已确认缺陷（按严重度）

### 高（confirmed）

1. **控制面任意 import。**
   - 路径：research/experiment.py:196 的 methods 检查只在 K 冻结了 methods 时才执行。没有 methods 时（v2 活动，或只配了 `[harness_evolution]`；主测试夹具 v06_prepared 就是这种形态），`worker.stop` 的 kind=model 改动可以通过准入。policies.py:270 允许 spec 里带 `backend`，:591 把它交给 `serving.backend`，serving.py:42-44 再调用 `build_backend`，最终在 config.py:77 `import_object(kind)(**spec)`。
   - 已离线 PoC 复现：import 并调用任意 callable。
   - 只是按代码路径推出、没有实际发请求验证的另一种后果：改成 openai_compat，就能把 `api_key_env` 指向的密钥发往任意 base_url。
   - 触发限制：R 的提示只告诉它 kinds `['rule','model']`（bench.py:517-523），没有提到 `backend` 键，要由 LLM 自己写出来。cycle 强制要求 `[improvement]`（bench.py:2013-2016），而它会冻结 methods。所以只有 improve/research 入口在没有 `[improvement]` 时可达，现有真实配置不受影响。
   - 这与"proposal 不受信、控制面不动态 import 候选"的设计不变量直接冲突。
2. **两支 W* 相同仍可判 R1 accepted 并安装**（campaign.py:328-381）。两支都没装任何东西时，外层差异纯属噪声，也会走到 accepted。tests/test_campaign.py:96-108 把这种情况断言成了预期（两支 installed 都是 0、control 为 budget_exhausted，结果 verdict == "accepted"）。
3. **外层比较不配对、不做完整性检查。** campaign.py:341-348 按每支自己剩下的有效任务求均值。外测不补跑（bench.py:1815-1836），也不预留额度。候选支有一道外测无效或 budget_exhausted 时仍可能判 accepted。严重度分歧：M6 复核定为 medium，E2E 复核定为 high。
4. **续跑不读 Experiment 冻结的 eval_template_ref 和 budget_scope。**
   - research/loop.py:346-356 只把 `expected_parent` 交给执行器；bench.py:748-749 和 :759-762 的 `_screen`/`_evaluate` 用的是当前的 `releases.active()` 和 `self.plan(...)`。
   - 后果：旧实验会用新 scope 的计划和预算续跑，并据此安装，已离线复现。
   - 不跨 scope 也会触发：在同一 scope 里重新冻结 task_plan_ref、预算不变时也一样。
   - 这两个冻结字段在所有路径上都只写不读；campaign 臂甚至记录了错误的模板（bench.py:1653）。

**代价。**
1. **安全**：最高危的缺陷就出在遗留面。`spec.backend` 本来是训练路径的合法载体（bench.py:740），在 K 没有 methods 时成了 R 可以触达的任意 import 入口。

3. **遗留路径自身的缺陷**：
   - `POST /outcome` 可以覆盖保留键：`type` 能把 dev 改写成 train，`ts` 决定账本文件路径，可以写到账本目录之外（ledger.py:129-130, 153-154）。中危。
   - `train_artifact` 吞掉 SystemExit，停机信号发出后循环仍继续付费（evolve/pipeline.py:396）。中危。
   - DT-08 的 attach 在生产中不可达。
   - TrainError 被判为 invalid、结算状态错误、training_seconds 没有上界，均为低危。
4. **规格冲突**：文档要求只对 on_finish 评分，与代码直接冲突。真实工作区里的 stop 决策大多是 per_turn，必须二选一。

## 8. 已证明与未证明

**已证明**（附前提）：
- 工程链路在离线替身下可以贯通，替身指脚本研究员、替换后的 `cycle_pairs` 和 `ProcessWorker(for_tests=True)`。
- 审计探针（不在仓库测试中）用"按 prompt 行动的假模型"驱动生产 PolicyResearcher，走完了 slot → accepted → 安装 R1 → 回用 verified。但这要加 `--gap-outer`，也就是人为把外层家族放在缺口上。改用生产的 `cycle_pairs` 后，slot-0 是 rejected。所以"按生产配对规则走到安装 R1"离线也没有证明过。
- v1 的 R 调用路径不接收 dev/final 明细。扫描真实的 4 个 context 和 3 条笔记，没有出现 dev 或 test 家族 id。
- 在预算簿层面，逐调用预留与结算、429 释放、unknown 不当作 0 都在真实运行中成立。但在报告和单次运行成本里，open 预留和 invalid 尝试的费用仍会消失（见 §5）。
- 文本草稿检查和修订在真实模型下可用，R 写的包能被真实加载。

**未证明**：
- **C1**：没有真实基线、没有安装、没有基于效果的 gate 结论。报告对 linkcheck2 算出的 "inconclusive: 1.0 against 0.0"，比的是 dev 上的 screen 结果和 train 上的测量结果，两者不可比。
- **C2**：机制在（report.py:245-255），但仓库没有 `external_references.json`，状态是 not_run。
- **C3**：属于第二版，报告标为 not_run，符合规格。
- **C4**：没有任何 campaign 记录。测试里的"接受"来自按调用顺序分配角色的脚本研究员。preset 的研究 gate 是 min_groups=1，外层约 13 题，significant 永远不会为 True。再叠加 §5 高危第 2、3 条，即使跑出 accepted 也可能是伪阳性。
- 还没有证据的部分：
  - 代码组件、hook、包工具在真实任务中执行。
  - Docker 中对 LLM 写的代码做草稿检查。
  - "下一包迭代"和"退化超上限被拒"。fixture 只有一个二值缺口，dev 中也没有重复发送风险，结构上演示不了。
  - 两项暂停修复在真实环境中复现。
- 统计功效：dev 约 25 个家族、repeats=1，按 ROADMAP §4 的自估只能识别约 +20pp 的效应；gate 用点估计判接受。
