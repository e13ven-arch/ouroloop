## (1) What it modifies

- Everything in a per-run copy of its own repository except `domains/` (the evaluation harness, scorers and datasets). Hunks touching `domains/` are stripped from every patch (`filter_patch_by_files(patch, ["domains/"])` in `utils/gl_utils.py::apply_diffs_container`) and reverted after the meta agent runs (`reset_paths_to_commit(paths=["domains/"])` in `run_meta_agent.py`). https://github.com/facebookresearch/HyperAgents/blob/main/utils/gl_utils.py, https://github.com/facebookresearch/HyperAgents/blob/main/run_meta_agent.py
- So mutable by the improver: `task_agent.py` (prompt, parsing, control flow), `meta_agent.py` (the improver itself), `agent/llm.py` (model constants, temperature, litellm call), `agent/llm_withtools.py` (the tool-use loop), `agent/tools/*` (new tools), `utils/`, `requirements.txt`, `README.md`; with flags also `ensemble.py` and `select_next_parent.py`. Paper: agents are "any computable program"; the meta agent "is tasked with modifying any part of the given codebase" (Sec. 3–4).
- Not model weights: the FM is frozen (Sec. 4). An SFT comparison lives in `baselines/sft_openai/` as a baseline only.
- The outer loop (`generate_loop.py`, parent selection, evaluation protocol) is copied into the sandbox but runs on the host, so edits to it have no effect: fixed by construction (paper Sec. 7 calls this a limitation; E.5 relaxes only parent selection).
- Caveat from code reading: `agent/llm.py` and the task agent's use of `self.model` are editable, and nothing checks that the evolved task agent still calls the domain's pinned model (`domains/paper_review/utils.py: MODEL = "gpt-4o"` is protected, but `TaskAgent` may ignore it). Whether any run did this is [unverified].

## (2) The improvement loop

- Entry point `generate_loop.py`: for `current_genid` in `range(start, max_generation+1)`: pick one parent, build a container, apply the parent's lineage of patches, run the parent's own meta agent once (6 h timeout), save its diff, import-check, evaluate, append to archive. One parent and one child per iteration in the released code; the paper's Algorithm 1 allows a sampled subset of parents (A.3). https://github.com/facebookresearch/HyperAgents/blob/main/generate_loop.py
- Iterations: 80 (Polyglot, matching DGM), 100 (paper review + robotics in one joint run), 50 for the imp@50 experiments, 200 for math grading (Sec. 5.1–5.3).
- Archive: `archive.jsonl` (append-only list of generation ids) plus `gen_N/metadata.json` (parent, patch list, `run_eval`, `run_full_eval`, `valid_parent`). Every child is appended; children with an empty diff, failed import or failed evaluation get `valid_parent=False` and are never selected again. If the meta-agent process exits non-zero, the parent is marked `valid_parent=False` (generate_loop.py lines 927–929).
- Parent selection (`select_parent`, method `score_child_prop`): score = validation score if the domain has one, else training score, averaged over domains; `s_i = sigmoid(10·(score_i − mean of top-3))`; weight `s_i · exp(−(children_i/8)^3)`; sample. Paper A.2 states the child penalty as `1/(1+n_i)`; the code uses `exp(−(n/8)^3)`, a discrepancy I could not reconcile.
- Initial hyperagent: task agent = one FM call with "You are an agent. Task input: ... Respond in JSON"; meta agent = one instruction "Modify any part of the codebase at `{repo_path}`." with bash + editor tools (A.1; `task_agent.py`, `meta_agent.py`).

## (3) Evaluation and selection of candidates

- Staged evaluation (Sec. 4.2, `utils/domain_utils.py`): 10 of 100 training tasks first; proceed to the full 100 only if score > 0 (Polyglot: ≥ 0.4 on 10 tasks); otherwise the unevaluated remainder counts as zero. Robotics: 3 reward-function samples, then 3 more if any is non-zero; average of 6.
- Splits (Table 2): Polyglot 60 train / 165 test, no val; paper review 100/100/100; robotics 6 train episodes / 6 test on a different task (walk forward → maximize torso height, `genesis_go2hop`); IMO grading 100/100/100. Splits are seeded random samples with a leak check on ids (`domains/paper_review/curate_subsets.py`, `domains/imo/curate_subsets.py`).
- Repeats: one evaluation per task at temperature 0 (o4-mini at 1.0; D.1). No repeats, no significance threshold for admission, no regression check: every compiled child enters the archive; regressions only lower its selection probability (A.4).
- Final: "Only the best agents, selected via validation scores (or training scores when validation tasks do not exist), are evaluated on the test set" (Sec. 5.1), once, on 100 test tasks (`domains/run_eval.py`). Statistics are over 5 runs per method: medians, 1,000-resample bootstrap CIs, Wilcoxon signed-rank (Sec. 5). Per-run raw test scores are hardcoded in `analysis/plot_testevals.py` (DGM-H paper review: 0.68, 0.71, 0.59, 0.75, 0.75).

## (4) Leakage controls

- Enforced in code: the meta agent's container receives a copy of all prior generations with `*_eval_val*`, `*_eval_test*`, `*_val*`, `*_test*` directories and files deleted (`generate_loop.py::copy_prev_eval_to_container`), so it sees only training evaluations; the scorer under `domains/` cannot be patched.
- Not enforced: the dataset CSVs with labels (`domains/paper_review/dataset_filtered_100_test.csv`, IMO equivalent) are copied into the sandbox where the meta agent has bash. Issue #39 (2026-08-19) shows a `gen_32` meta-agent chat history reading a test sample and its label; fix PR #42 (2026-09-02) is open and unmerged, no maintainer comment. https://github.com/facebookresearch/HyperAgents/issues/39, https://github.com/facebookresearch/HyperAgents/pull/42. I confirmed the root cause in `setup_initial_gen`'s `excluded_dirs_domains`. Whether the published runs were affected is [unverified].
- Validation is used both for parent selection and for choosing the test candidate (standard, mild optimism). The paper's cleanest unseen evaluations are Polyglot's 165 held-out tasks (C.1), robotics' different test task (C.3) and the transfer to IMO grading, a domain the source runs never saw (Sec. 5.2).

## (5) Is the improver improved, and how is that validated

- Yes by construction: `meta_agent.py` is in the editable program; one patch may change `task_agent.py` and `meta_agent.py` together, and selection sees only task score. Meta-level edits are therefore never validated individually; they ride along with task gains.
- Validation offered: (a) ablation "DGM-H w/o self-improve" runs the initial meta agent from a `DONOTTOUCH_` copy for the whole run (generate_loop.py lines 485–493; paper 4.1): test 0.0 (CI 0.0–0.130) vs 0.710 on paper review, 0.213 (0.180–0.348) vs 0.372 on robotics, p < 0.05 over 5 runs. (b) imp@k (D.3): a fixed meta agent gets k=50 generations from a given task agent; imp@50 = best-by-val agent's test score minus the start. A transfer hyperagent chosen by the lineage-discounted "growth score" G_0.6 over descendants with ≥ 3 children (D.4, `analysis/transfer_utils.py`) scores imp@50 = 0.630 (0.540–0.630) on IMO grading vs 0.0 (0.0–0.130) for the initial meta agent and 0.0 for DGM-custom transfers (Sec. 5.2). (c) Compounding: 200 iterations from transfer agents 0.640 (0.550–0.720) vs 0.610 (0.510–0.680) from scratch, not significant (Sec. 5.3).
- The paper "qualitatively attribute[s]" the transfer to emergent performance tracking and persistent memory (Sec. 5.2, E.3); no ablation isolates those features.

## (6) Reported results

- Models (D.1; `agent/llm.py`): meta agent Claude 4.5 Sonnet (`anthropic/claude-sonnet-4-5-20250929`), Claude 3.5 Sonnet (New) on Polyglot; task agents GPT-4o (paper review), Claude 4.5 Sonnet (robotics), o4-mini (IMO), o3-mini (Polyglot).
- Polyglot (same model as DGM): train 0.140 → 0.340 (0.300–0.380), full benchmark 0.084 → 0.267 (0.231–0.280); DGM reported 0.140 → 0.380 and 0.142 → 0.307 (Sec. 5.1).
- Paper review test (100 tasks, median of 5 runs): initial 0.0; DGM-H 0.710 (0.590–0.750); DGM-custom 0.590 (0.570–0.650); DGM 0.0 (0.0–0.510); w/o self-improve 0.0 (0.0–0.130); w/o archive 0.0 (0.0–0.560); AI-Scientist-v2 static reviewer 0.630. DGM-H vs DGM-custom not significant.
- Robotics test: initial 0.060; DGM-H 0.372 (0.355–0.436); DGM-custom 0.348; DGM 0.0 (0.0–0.090); w/o self-improve 0.213; w/o archive 0.116; default reward 0.348.
- IMO grading: ProofAutoGrader as task agent + transferred meta agent → 0.700 vs 0.670 on the 100-task test; full IMO-GradingBench accuracy 0.561 → 0.601, MAE 0.178 → 0.175 (Sec. 5.3).
- Cost (D.2): ~33M tokens of self-modification per 100 iterations plus 0.506M tokens of evaluation per iteration ≈ 88.6M tokens per 100-iteration paper-review+robotics run; 5 runs per method; no dollar figure. HN commenter "yurimo" cites the same ~88M figure.

## (7) Failure modes they report

- Initial agents score 0 for format reasons (no parsing); initial reward functions fail to compile (Sec. 5.1). Staged eval treats unevaluated tasks as zero.
- AI judges "are more likely to overfit to the training data", hence the validation split (Sec. 4.2). No overfitting or gaming incident is reported; Appendix F discusses "evaluation gaming" (Goodhart) as a risk only.
- Letting the agent edit parent selection did not beat the handcrafted rule: 0.428 random, 0.491 modifiable, 0.532 handcrafted, not significant; the evolved UCB/softmax variants were "complex and sensitive" (E.5).
- Noise: paper-review per-run test scores span 0.59–0.75 for the same method; n = 5 runs.
- External: issue #28 reports a reproduction gap with GPT-5.2 as meta agent, noting the unmodified meta agent "only makes trivial modification to README.md" and the task agent emits summaries instead of decisions https://github.com/facebookresearch/HyperAgents/issues/28; issue #30 notes `eval_path` and `iterations_left` are accepted by `MetaAgent.forward` but never put in the prompt (confirmed in code; the evolved agents in E.3.2 do use `iterations_left`, so the released initial agent and the paper's Sec. 4 description differ at the prompt level) https://github.com/facebookresearch/HyperAgents/issues/30; Roesner and Kohno (arXiv:2609.17817, 2026-09-15) poison a benchmark and report that "Hyperagents powered by Sonnet 4.5" self-evolved instructions that disable HTTPS certificate validation on neutral tasks https://arxiv.org/abs/2609.17817.

## (9) Agent and harness design

- Agent loop (`agent/llm_withtools.py::chat_with_agent`): one conversation; a system preamble lists tools and demands exactly one `<json>{"tool_name","tool_input"}</json>` per response; the tool result is appended as the next user message; the loop ends when a response contains no tool call. `max_tool_calls=40` per invocation; a retry message is sent when a response looks like a truncated tool call (≥ 2000 chars). No planner/executor split, no memory, no context management (history grows unbounded; `MAX_TOKENS=16384` output), no finish check, temperature 0 via litellm with exponential backoff. Tools: `bash` (persistent `/bin/bash -i`, 120 s per command) and `editor` (view/create/str_replace/insert/undo_edit), the DGM tool set.
- Task agent: one call, no tools, must emit `<json>{"response": ...}</json>`; parse failure → prediction "None" (`task_agent.py`). Meta agent: same loop with `tools_available='all'`, one-line instruction; the sandbox README (written by `get_readme_description`) tells it to "look at its code repository and the provided path to previously generated agents and their evaluation results"; prior generations are copied to `/tmp/<run>/gen_*/` (train `predictions.csv`, `report.json` with `question_ids_failed/passed` and per-label precision/recall, per-task `chat_history_<id>.md`, patches, metadata, prior meta-agent chats). Timeouts: meta agent 21,600 s; evaluation 18,000 s per domain; report 10,800 s; import check 300 s.
- Harness (`utils/gl_utils.py::setup_initial_gen`): per run, copy the repo to `outputs/generate_<id>/gen_initial/hyperagents` excluding `outputs/ analysis/ baselines/ Dockerfile setup_initial.sh`, copy only the active domains, write the README, `git commit` as the root. Mutable surface: everything in that copy except `domains/`.
- Change representation and versioning: a unified diff `model_patch.diff` (git diff vs base commit plus untracked files, `utils/git_utils.py::diff_versus_commit`). A node's code = root commit + ordered `prev_patch_files + curr_patch_files`, reapplied with `patch -p1` in a fresh container each time; lineage lives in `metadata.json`; rollback is implicit (select another parent); nothing is deleted. Transfer experiments reuse patches with `--meta_patch_files`, optionally stripping `task_agent.py` or `meta_agent.py` hunks (`process_meta_patch_files`).
- Isolation and testing: one Docker container per generation (and per ensemble or parent-selection call), image from `Dockerfile` (nvidia/cuda base), repo bind-mounted read-write from the host, `network_mode="host"`, GPU passthrough for Genesis; after each generation `git reset --hard root && git clean -fd`. The bash tool's description says "You don't have access to the internet", and the paper says "restricted internet access" (Sec. 6), but the released code does not enforce it [unverified beyond code reading]. Pre-use tests: `python -c "from meta_agent import MetaAgent"` and `from task_agent import TaskAgent` only, then the staged evaluation; an empty diff skips evaluation.

## (10) Self-improvement design

- Signal: raw artifacts on disk, not summaries: every prior generation's training predictions, per-task chat histories, reports with failed/passed ids, patches and the meta agents' own transcripts. The initial meta agent has no diagnosis step at all; by contrast the DGM-custom baseline samples one random failed task and runs a fixed diagnose prompt that returns one `improvement_proposal` and a GitHub-issue-style `problem_description` (`baselines/dgm/utils.py`; paper Appendix B).
- Per-task vs aggregate: left to evolution. E.3.1 shows an evolved `_analyze_evaluations()` that aggregates; E.3.6 shows per-generation summaries ("Gen 55: 63% accuracy, 75% reject rate ... Gen 66: 52%, 6% reject rate") driving the next prompt edit.
- Avoiding refuted ideas: no built-in mechanism. The archive is readable, and agents evolved a `MemoryTool` (`memory.json`), a `PerformanceTracker` (`performance_history.json`) and prompt-template systems (E.3.4, E.3.5, E.3.7). Novelty pressure exists only in parent selection (child-count penalty).
- Stopping: a fixed iteration budget (`--max_generation`), no convergence test; `iterations_left` is passed to the process and evolved agents branch on it (E.3.2); the best agent is chosen afterwards by validation score.

## For reharness

- Borrow: (a) the archive with stepping-stone parent selection: DGM-H's winning lineages "pass through intermediate nodes with lower performance" (E.2), while reharness discards a rejected candidate; keeping rejected-but-valid packages as selectable parents with a child-count penalty is bookkeeping, not a new module. (b) A staged smoke evaluation (10 tasks, score > 0) before the full gate; reharness paid full 25-task gates for the −8-point regressions in v0.2. (c) imp@k and the lineage-discounted growth score as the C4 statistic: "best W after k proposals from the same W0" per arm, which is what the research slot already produces, instead of a single accepted/rejected round.
- Already better: the sealed, pre-committed, paired final (DGM-H runs the best-by-val agent once on test and its sandbox contained the test labels, issue #39); explicit admission (min_gain plus regression tolerance; DGM-H admits every compiled child with no regression check); the budget ledger with per-call reservations (DGM-H has a post-hoc token estimate only); R recursion validated by downstream W* from the same W0/E0 and installed only after the gate (DGM-H never validates a meta-agent edit on its own; it ships in the same patch as task edits).
- Already better, isolation: reharness's generated code cannot reach the scorer, provider or budget; DGM-H protects only `domains/` by patch filtering, and `agent/llm.py` (model choice) is editable.
- Trap: "modify anything" plus score-only selection is a Goodhart machine the paper itself names (Appendix F) and the poisoned-benchmark paper exploits; do not widen reharness's mutable surface toward model, provider or evaluation code to chase DGM-H's breadth.
- Trap: the memory and performance-tracking "mechanisms of improvement" are a qualitative attribution over 5 seeds with 0.59–0.75 per-run spread, the same noise floor reharness measured (W0 at 41.3% and 47.8%); treat them as hypotheses to test with a gate, not as a design to copy.
