Sources read: the repo at main commit `fb1ed58` (2026-10-02), cloned to the scratchpad; the ICLR 2026 paper v2 (2026-02-14); the docs site, guides and blog posts shipped in `docs/`; GitHub API metadata; issues #133/#139/#379; and three third-party sources. Everything below is cited; items I could not verify are marked **[unverified]**. Local paths for reharness context: `docs/DESIGN.md`, `docs/RESULTS.md`.

## 1. What it modifies

- **Core GEPA (`gepa.optimize`)**: a *candidate* is `dict[str, str]`, named text components; "GEPA evolves only the set of prompts... whereas the underlying LLM weights remain fixed" (paper §3, https://arxiv.org/pdf/2507.19457v2 p.4). Model weights are never touched.
- **`optimize_anything`** generalizes the component to any text: prompts, code, agent code, scheduling policies, SVG, skills. Modes are selected by which sets you pass: single-task (`dataset=None`), multi-task (`dataset` only), generalization (`dataset`+`valset`) (https://github.com/gepa-ai/gepa/blob/main/docs/docs/blog/posts/2026-02-18-introducing-optimize-anything/index.md).
- Concretely evolved artifacts in the repo: whole agent Python source for ARC-AGI (`examples/arc_agi/main.py`: "GEPA optimizes the agent's Python code (not a prompt)"); a Terminus `instruction_prompt` for Terminal-Bench (`src/gepa/adapters/terminal_bench_adapter/terminal_bench_adapter.py`); SKILL.md-style skill text for coding agents (`src/gepa/gskill/`); full DSPy programs (`src/gepa/adapters/dspy_full_program_adapter/`).
- **The improver itself**: the reflection meta-prompt is a fixed class constant (`InstructionProposalSignature.default_prompt_template`, `src/gepa/strategies/instruction_proposal.py`) and the paper's Appendix C prints it as fixed. Note: an automated page summary I got from WebFetch claimed "reflection prompts are dynamically evolved"; that is wrong per Appendix C and the source. See §5 for the one partial exception (refiner).

## 2. The improvement loop

- Proposer: one reflection LM call per component per iteration (`StatelessReflectionLM`), or a custom proposer / Claude Code agent (`src/gepa/oa/proposers/claude_code_agent.py`).
- Per iteration (Algorithm 1, paper p.6; `src/gepa/core/engine.py` `run()` and `src/gepa/proposer/reflective_mutation/reflective_mutation.py` `propose()`): (1) select a parent from the Pareto front; (2) sample a minibatch of `reflection_minibatch_size` train examples (default 3; paper used 3) via `EpochShuffledBatchSampler`; (3) evaluate parent with traces; (4) build a reflective dataset for one component (round-robin by default, `all` optional); (5) reflect, producing a **full replacement text** for that component; (6) evaluate child on the same minibatch; (7) accept if the sum strictly improves; (8) on accept, evaluate on the full valset and add to the pool with its parent id.
- Candidates per iteration: default 1 (`SingleMutationSampling`). Since v0.1.4, `PxNSampling(p, n)` gives p parents × n mutations with `AllImprovements`/`BestImprovement`/`TopKImprovements` selection (https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/parallel-proposals.md).
- Iterations: not fixed; the loop runs until a stopper fires, mainly `max_metric_calls` (counted in rollouts = candidate × example evaluations). Paper budgets per benchmark were matched to MIPROv2's rollouts, 1,839–7,051 (Table 1, p.8).
- Archive/population: `GEPAState.program_candidates` holds every accepted candidate; `parent_program_for_candidate` records lineage (merges have two parents); per-instance Pareto maps `pareto_front_valset` / `program_at_pareto_front_valset` (`src/gepa/core/state.py`). Pareto selection samples a non-dominated candidate with probability proportional to how many val instances it is best on (Algorithm 2, p.6; `src/gepa/strategies/candidate_selector.py`). Merge ("system-aware crossover") combines two descendants of a common ancestor that changed disjoint components, at most `max_merge_invocations=5`, accepted if the merged subsample score ≥ max(parents) on 5 val ids (`src/gepa/proposer/merge.py`; paper Appendix D.1).

## 3. Evaluation and selection

- Splits: `trainset` (`D_feedback`) feeds reflection minibatches; `valset` (`D_pareto`) is the selection set: full-valset evaluation of each accepted child, Pareto bookkeeping, and the final pick = argmax of mean val score (`FullEvaluationPolicy.get_best_program`, `src/gepa/strategies/eval_policy.py`). **If `valset` is omitted, GEPA reuses the trainset** (`src/gepa/api.py` docstring), i.e. no held-out selection at all.
- Task counts in the paper: HotpotQA 150/300/300 train/val/test, IFBench 150/300/294, HoVer 150/300/300, PUPA 111/111/221, AIME 2022–24 split train/val and AIME-2025 (30 questions × 5 repeats) as test, LiveBench-Math 368 split equally (Appendix E.1, pp.23–25). Docs recommend 80/20 above 200 examples, 50/50 below, and a budget of 15–30× `len(valset)` (https://gepa-ai.github.io/gepa/guides/faq/).
- Repeats: none in the engine; one rollout per (candidate, example) ("Stochastic N=1 default", `.claude/skills/gepa-optimize-anything/references/gotchas.md`; issue https://github.com/gepa-ai/gepa/issues/139 is open). Evaluation cache (`cache_evaluation`, off by default) returns the stored score for an identical candidate.
- Statistical threshold: none. Acceptance is `sum(after) > sum(before)` on the ~3-example minibatch (`StrictImprovementAcceptance`; `improvement_or_equal` optional). The docs state the weakness themselves: "a large regression on one example can mask improvements on others" (https://github.com/gepa-ai/gepa/blob/main/docs/docs/guides/acceptance-criterion.md).
- Regression check: none per instance. Merge is the only step with a ≥ parents rule.
- Held-out final: the paper evaluates the val-best candidate on a test split once (Table 1/2 and the "test-set star" in Figure 1). `optimize_anything(test_set=...)` scores seed and best outside the budget and reports `metadata["test_score"]` and `["baseline_test_score"]` (`src/gepa/optimize_anything.py`). No confidence intervals or multi-seed variance in the main tables **[unverified: I did not find seeds reported; I did not read every appendix figure]**.

## 4. Leakage controls

- The reflection LM sees train traces only; the proposer sees per-instance val *scores* (via the Pareto front) but not val content: "direct access to the content of validation instances is restricted" (paper p.8). Merge's 5-id subsample is drawn from the valset (`select_eval_subsample_for_merged_program`), so val rollouts are spent on acceptance, not reflection.
- The eval cache is namespaced by split since a bug where "contaminated distinct-valset entries" could be served from trainset rollouts at the same index; old unsplit keys are dropped on load (`src/gepa/core/state.py` `EvaluationCache` docstring).
- `test_set` "never enters the eval server, so engines and agents cannot see it" (`src/gepa/optimize_anything.py`). The ARC example holds val out of the HF training split and uses the full evaluation split as test (`examples/arc_agi/README.md`).
- **Exception**: the agentic engines `meta_harness` and `autoresearch` merge train and val into one visible pool: "The proposer sees one combined 'training' set and never knows val existed; test stays sealed at the eval-server HTTP layer" (`src/gepa/oa/engines/meta_harness.py` `_materialize_sandbox`). So those engines have no held-out selection, only a sealed test for reporting.

## 5. Is the improver improved, and how is it validated?

- Not automatically. The meta-prompt is fixed (Appendix C; `instruction_proposal.py`). The FAQ's "Can GEPA's meta-prompt itself be optimized? Yes!" means you may hand-write a custom `instruction_proposer` or template (https://gepa-ai.github.io/gepa/guides/faq/), not that GEPA learns it.
- Partial exception: `RefinerConfig` (off by default, `refiner: RefinerConfig | None = None`) calls an LLM after each evaluation to refine the candidate and keeps the better of (original, refined); "A `refiner_prompt` parameter is auto-injected into seed candidates and co-evolved alongside the other parameters" (`src/gepa/gepa_launcher.py` lines ~805–823). That co-evolved refiner prompt is accepted by the same minibatch/valset rule as any component; there is no separate comparison of improver quality (nothing like reharness's R0 vs R1 by downstream W*).
- The Claude Code proposer and meta-harness read a fixed `SKILL.md` and a rebuilt `history.md`; nothing rewrites those (`src/gepa/oa/engines/meta_harness.py` `SKILL_MD`).
- `omni` composes engines (run GEPA/AutoResearch/Meta-Harness on $5 each, continue the best on $15); it selects an optimizer, it does not modify one (`docs/docs/blog/posts/2026-07-22-optimize-anything-omni/index.md`).

## 6. Reported results

Paper (https://arxiv.org/abs/2507.19457, ICLR 2026 oral), single run per config as far as reported:
- Qwen3-8B aggregate over six tasks: baseline 45.23, GRPO 48.91 (24,000 rollouts, LoRA), MIPROv2 47.84, GEPA 54.85 (+9.62), GEPA+Merge 52.40. GEPA rollouts 1,839–7,051 (mean 3,936). Per task GEPA: HotpotQA 62.33 (base 42.33), IFBench 38.61 (36.90), HoVer 52.33 (35.33), PUPA 91.85 (80.82), AIME-2025 32.00 (27.33; GRPO 38.00 beats it), LiveBench-Math 51.95 (48.70) (Table 1, p.8).
- GPT-4.1-mini aggregate: baseline 53.03, MIPROv2 58.67, TextGrad 59.14, GEPA 65.22 (+12.19), GEPA+Merge 66.36; prompts optimized on Qwen3-8B transfer to GPT-4.1-mini at +9.00 (Table 2, p.8). Cost: "under $500 to run all experiments in Table 2"; GEPA $86, GEPA-Merge $67, MIPROv2 $76 (Appendix E.3, p.25).
- "The majority of GEPA's rollout budget is spent on validation"; counting only train rollouts, 79–737 reach the optimum (Observation 1, p.9).
- Blog/README claims (same authors, not peer-reviewed): ARC-AGI v1 with Gemini 3 Flash, val 56.5→93.5, test 32.5→89.5, one run, test n = full evaluation split, cost ~2× per task (`docs/docs/blog/posts/2026-02-18-introducing-optimize-anything/index.md`); gskill: Mini-SWE-Agent + gpt-5-mini 55→82% (Jinja) and 24→93% (Bleve) on ~60-task test splits under 300 rollouts, skills transfer to Claude Code (`docs/docs/blog/posts/2026-02-18-automatically-learning-skills-for-coding-agents/index.md`); parallel proposals: 2×2 raises LiveBench-Math test 68.9→72.1 and 8×1 raises HoVer 49.0→60.0 at the same budget, with the val→test gap 9 points for single-mutation vs 2 for 2×4 (`docs/docs/blog/posts/2026-07-30-parallel-proposals/index.md`); "optimize cheap, deploy strong": HotpotQA 59.4 vs 50.4 at $7 vs $102, pooled +2.8 (95% CI [+1.3, +4.4]) over 48 setups (`docs/docs/blog/posts/2026-09-29-optimize-cheap-deploy-strong/index.md`).
- Third party: Decagon (2026-03-25) in production classification: scaling 50→500 training samples made prompts 75% longer and performance 2% worse at 10× compute; a 1,500-character cap gave 4× compression at −0.8%; sweet spot 20–100 samples (https://decagon.ai/blog/optimizing-gepa-for-production). MAGE (2026-07-11): on GSM8K-Hard with gpt-4o-mini, 5 seeds, MAGE 46.4% vs GEPA 34.0%, seed-to-seed variance ~7% for both (https://arxiv.org/abs/2607.11944). A search snippet attributed "unoptimized seed 62.4%" to one of these papers; **[unverified]**, I did not confirm the source.

## 7. Failure modes they report

From the repo's own `gotchas.md` and FAQ: reward hacking ("a correctness-only score drove the optimizer to a prompt that tells the model to wrap the reference implementation", KernelBench); winner's curse on `valset` with N=1 scores ("a selected best of 0.87 with runner-up 0.60 and median 0.57"); "baseline saturation" (seed near-perfect on minibatches → zero accepted proposals); copying usernames/document titles from training minibatches (Dropbox); task drift (changing a 1–5 scale to 1–3); prompt bloat ("GEPA does not aim for brevity"); budget overshoot under P×N. Paper Observation 5: GEPA+Merge degrades on Qwen3-8B (IFBench 38.61→28.23) because merge timing is untuned. Open issues: no memory of rejected proposals, so a sticky parent repeats the same broken mutation (https://github.com/gepa-ai/gepa/issues/379, fix proposed in PR #384); single rollout per task (#139); k-fold selection to reduce val overfitting (#133); anti-overfit guard (#261); mutation-rate control (#277).

## 9. Agent and harness design

- **No agent loop in GEPA.** The "system" is a black box behind `GEPAAdapter.evaluate(batch, candidate, capture_traces) -> EvaluationBatch(outputs, scores, trajectories, objective_scores)` and `make_reflective_dataset(candidate, eval_batch, components_to_update) -> {component: [records]}` (`src/gepa/core/adapter.py`; `src/gepa/adapters/README.md`). Planner/executor, tool protocol, memory, stop checks and retries are entirely the adapter's or the user's agent framework's (DSPy, LangChain, Terminus, Mini-SWE-Agent). The Terminal-Bench adapter shells out to `tb run`, writes the candidate prompt to a template file, and reads back `results.json` plus the last episode's `debug.json`; feedback is "Failed to solve the task. Reason: {failure_mode}" plus the message history.
- **Mutable surface = text components.** Whatever is in the candidate dict is mutable; everything else is frozen. Prompts, skills, config, or a whole Python module (ARC: `solve(train_inputs, train_outputs, test_inputs, llm)` with `max_llm_calls=10` and a cost penalty `score = test_score - 0.1*(cost > $1)`). No notion of middleware/hooks/tools as separate typed objects; the DSPy full-program adapter mutates the program source as one string.
- **Change representation**: full replacement text per component, returned inside a ``` fence and parsed by `ProposalAdapter` (truncated outputs are rejected rather than salvaged). No diffs or DSL; the FAQ suggests a "smallest possible targeted edit" template for production.
- **Versioning**: an append-only pool with parent ids, discovery budget per candidate, per-instance Pareto maps, `gepa_state.bin` checkpoint each iteration with resume; with `write_agent_state=True` an on-disk tree `iterations/<id>/{meta.json, components/, trace.json, val_scores.json, outputs/, trajectories/}`, `pareto/*.json`, `history.md`, `candidate_tree.html` (`src/gepa/core/state.py`; `src/gepa/api.py`). "Rollback" is not a concept: nothing is installed; the best-by-val-mean is picked at the end.
- **Isolation of generated code**: `gepa.utils.code_execution.execute_code` offers `IN_PROCESS` (plain `exec`) or `SUBPROCESS` with timeout, stdout capture and pickled variables; no container. For Claude-Code-driven proposers/engines: bwrap jail on Linux, Seatbelt on macOS, `WebFetch/WebSearch` denied, network shared with the host, and "Write isolation across concurrent proposers is convention-only" (`src/gepa/oa/sandbox.py`, `src/gepa/oa/proposers/claude_code_agent.py`). **No test of a generated candidate before it is used**: the minibatch evaluation is the test; an exception in the evaluator aborts the run by default (`raise_on_exception=True`) or scores 0. Whether the ARC example runs agent code in a subprocess I did not check (`examples/arc_agi/utils.py`) **[unverified]**.
- **Reflection context management**: records rendered as markdown (`# Example i / ## key`), ~3 per call; ComBEE map-shuffle-reduce (`k = ⌊√n⌋` groups, `k+1` calls) for minibatches ≥ 20 (`docs/docs/guides/combee.md`); images allowed. Reflection failures fall back per task (`_propose_texts_batch_safe`).
- **Meta-harness engine** (closest to "harness evolution"): a Claude Code session reads `task.md`, `frontier.json` (overall best plus per-example winners), `evolution_summary.jsonl` (hypothesis, axis exploitation/exploration, delta, outcome), `state/eval_traces/`, writes ≤3 candidate files per iteration plus `pending_eval.json`; the engine scores them, updates the frontier (strict-greater), and loops up to 50 iterations or budget. Its SKILL.md forbids parameter-only variants and example-specific hints and mandates prototyping in `scratch/` (`src/gepa/oa/engines/meta_harness.py`).

## 10. Self-improvement design

- **Signal**: per-example records of inputs, outputs and textual feedback from the metric/`side_info`/`oa.log()` ("Actionable Side Information"), plus scores; traces are whatever the adapter serializes. The meta-prompt instructs: "Identify all niche and domain specific factual information about the task and include it in the instruction... The assistant may have utilized a generalizable strategy... include that in the instruction as well" (`instruction_proposal.py`; paper Appendix C).
- **Diagnosis granularity**: per minibatch (default 3 examples, successes and failures), one component at a time, collapsed into one rewritten text. No per-task notes, no aggregate over the history; `skip_perfect_score` skips minibatches with no failures.
- **Avoiding refuted ideas**: nothing in core; rejected proposals are discarded (issue #379). Indirect diversity comes from epoch-shuffled minibatches, Pareto sampling across parents, duplicate-candidate dedupe within an iteration, and `merges_performed` bookkeeping. The Claude Code proposer rebuilds `history.md` (plan + score per past iteration) and the meta-harness keeps `evolution_summary.jsonl` and post-eval reports, which is the only explicit "memory of experiments".
- **Stopping**: budget (`max_metric_calls`, `max_reflection_cost`/`max_token_cost`), `NoImprovementStopper`, `ScoreThresholdStopper`/`stop_at_score`, timeout, `gepa.stop` file, signal (`src/gepa/utils/stop_condition.py`); meta-harness also stops on empty `pending_eval.json` or proposer failure.

## What reharness could borrow, already does better, and should avoid

- **Borrow**: (a) a per-task Pareto archive over dev results instead of one active package, so a candidate that wins specific families survives for later merge; the parallel-proposals post is evidence that committing several proposals before adapting to the selection set shrinks the val→test gap (9→2 points), which is reharness's largest problem (dev 80–84% vs test 52%, `docs/RESULTS.md`); (b) a cheap pre-gate: re-run the exact failing train tasks the notes came from before paying a 25-task dev gate, which is GEPA's minibatch screen; (c) an evaluation cache keyed by (package hash, split, task) so W0 is not re-measured three times at the same score; (d) a structured experiment ledger with hypothesis/axis/delta per candidate, which is what R1 asked for in v0.2 and what issue #379 asks GEPA to add; (e) the "optimize cheap, deploy strong" and gskill transfer results suggest evolving on a cheaper actor and sealing the final on the deployed one, worth a budgeted test given $373 per activity.
- **Already better in reharness**: a sealed, pre-committed final with bootstrap intervals (GEPA reports one test number, no CI, no seeds); per-task regression checks in the gate (GEPA has none); a budget root with reservations (GEPA counts rollouts and reflection dollars only); isolated Docker workers, package API, and draft import/interface checks before paid evaluation (GEPA runs evolved code via `exec`/subprocess and tests nothing before use); and R recursion with an R0/R1 downstream comparison (GEPA's improver is fixed; the refiner's co-evolved prompt is never validated separately).
- **Traps**: per-task "best" selection on 25 dev tasks with one rollout each is mostly noise at reharness's ±6-point floor; GEPA's own gotchas warn that the selected max is inflated and that N>1 is needed. Accepting on 3-example strict improvement is a coin flip at that variance. Prompt and hook bloat is a documented GEPA outcome (Decagon's +75% length, −2% accuracy; reharness's W* already costs $0.570 vs $0.452 per attempt). Do not copy "evolve the whole agent as one text blob" or the agentic engines' merged train+val pool; both discard the isolation and leakage controls reharness has. Treat the ARC 32.5→89.5 figure as one selected run on an unreported n, not a typical gain. Assertion-scored benchmarks are gameable the way KernelBench was; a hook that spams every channel could pass assertions, so keep the regression check.
