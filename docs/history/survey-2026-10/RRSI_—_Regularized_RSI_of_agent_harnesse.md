## (1) What it modifies

Only the **harness source directory** of a frozen-policy agent; never weights, never the tool environment, grader or task set, never the improver. The editable vocabulary `K = {prompt, control_flow, config, output_plumbing, context_mgmt, client_tool, skill, memory, subagent}` is fixed in `rrsi/components.py` and paper Eq. 12 (https://github.com/google-research/rrsi/blob/main/rrsi/components.py). Per domain the mutable tree is `Domain.harness_path`: coding `third_party/harbor_terminus2/` (agent loop `terminus_2.py`, JSON/XML response parsers, `templates/*.txt` prompts, `tmux_session.py`, `mechanisms.py`), workspace/eng `third_party/archipelago/harness_{workspace,eng}/` (`main.py` ReAct loop, `tools.py` meta-tools, `resum.py` context compression, `tool_result.py` truncation, `prompts.py`, `mechanisms.py`) (https://github.com/google-research/rrsi/blob/main/domains/coding/adapter.py, https://github.com/google-research/rrsi/blob/main/domains/eng/adapter.py). Frozen by contract (SKILL.md hard rule 5): entry-point class names, trajectory schema, and anything injected by the runner — model name, `max_steps`, timeouts, concurrency — "editing them is a wasted edit" (https://github.com/google-research/rrsi/blob/main/domains/coding/SKILL.md). The MCP tool gateway is explicitly "the benchmark's world, not the agent's scaffold, and the proposer never edits it" (https://github.com/google-research/rrsi/blob/main/domains/eng/mcp_gateway/gateway.py). The improver's own prompts (`SKILL.md`, `PATTERNS.md`, `briefs.py`, the templates in `propose.py`/`analyst.py`/`critic.py`) are plain files outside the harness path and are never candidates.

## (2) The improvement loop

- **Proposer**: one Claude Opus 4.8 "harness engineer agent" per candidate, editing files in place through a strict-JSON action protocol (`list_files/read_file/list_traces/read_trace/edit_file/write_file/done`), max 40 turns and 80 file edits per candidate; `edit_file` requires the `old` substring to occur exactly once; `write_file` is for new files only; paths are jailed to the harness dir and to `source_exts` (https://github.com/google-research/rrsi/blob/main/rrsi/propose.py). There is **no abort**: "THERE IS NO ABORT ACTION. You must ship a candidate" (three abort attempts are bounced before one is accepted as `no_proposal`).
- **Candidates per round**: `m = 2` in all three `rrsi.json` (README: "Each round drafts two candidates in their own git worktrees") (https://github.com/google-research/rrsi/blob/main/domains/coding/rrsi.json). When stalled, the last `m_draft = 1` slot is reserved for a never-exercised component (`loop.py` line `reserved = bool(sigma and explore["untried"] and v >= cfg.m - cfg.m_draft)`).
- **Edits per candidate**: annealed L0 budget `b_t = ceil(b_min + (b_max − b_min)·½(1+cos(πt/T)))`, `b_max = 4/3/4`, `b_min = 1` (paper Table 5; `rrsi/schedule.py`). Issue #2 shows the released schedule never reaches 1; the maintainer confirmed "every reported run used a final-round budget of 2" (https://github.com/google-research/rrsi/issues/2).
- **Rounds**: `T = 20` (coding), `20` (workspace), `40` (eng) (Table 5). No stopping rule: the driver runs `t = 0..T−1`; `touch runs/<domain>/STOP` stops manually; 3 consecutive unsettled rounds abort (https://github.com/google-research/rrsi/blob/main/rrsi/driver.py).
- **Archive/population**: none. Single incumbent `H_t` on branch `evolve/<domain>`; greedy argmax among admissible; "no population or archive maintained" (paper C.1, Alg. 2). Evaluated candidate branches `<domain>/r<t><variant>` and `runs/<domain>/r<t>/<v>/diff.patch` persist as lineage; gate-failed branches are deleted.

## (3) Evaluation and selection

- **Split and n**: both candidates are evaluated on the **entire evolve set** with `k` trials per task: coding 89 tasks × k=2 = 178 trials; workspace 120 tasks × k=2 (score = criteria passed / ~14,100 criterion verdicts, weighted by rubric length); eng 61 tasks × k=4 = 244 trials (paper A.1–A.7, D.1; domain READMEs https://github.com/google-research/rrsi/blob/main/domains/workspace/README.md). A missing/crashed trial counts 0 with the full denominator (`rrsi/evaluate.py`); if > `invalid_missing_frac` (0.2/0.1/0.15) of trials are missing the eval is retried once then marked `eval_invalid` (infrastructure, not a rejection).
- **Statistical threshold**: a noise band δ, **hand-fixed in the release** at 0.017 / 0.004 / 0.020 ("3 passes of 178", "60 criteria of ~14,100", "5 passes of 244"); `rrsi/calibrate.py` can re-estimate δ = 2·sd(null ΔS) only when `delta` is `null` (README "Method to code"; https://github.com/google-research/rrsi/blob/main/rrsi/calibrate.py). `baseline` writes `calibration.json` but `Run.delta()` returns the fixed constant when set (`rrsi/loop.py`).
- **Admissibility (Alg. 2, `rrsi/selection.py`)**: (a) floor `S' ≥ S* − δ` where `S*` is the **best score ever seen**, not the incumbent; (b) if `ΔS > δ`: `ΔC ≤ β0 + β1·ΔS` with ΔC relative policy-tokens/trial (β0 = 0.10/0.10/0.15, β1 = 44.5/35.4/24.4); else the within-band rule `w_s·ΔS − w_c·ΔC + w_n·ν > 0` (coding `w_s = 0`, so a within-band score gain alone never admits; a token saving or a never-accepted structural component type does); (c) domain guards, eng only: valid-rate drop > 0.03 or no-submission rise > 0.02 rejects. Winner = argmax S' among admissible; else keep `H_t`.
- **Regression check**: none in selection. Per-task drops (≥ 1/k, workspace 0.05) are computed only as an "attribution scoreboard" of predicted hits vs `unpredicted_regressions` shown back to the proposer (`Run.attribute`, https://github.com/google-research/rrsi/blob/main/rrsi/loop.py).
- **Held-out final**: Harvey LAB only has an in-distribution held-out (40 tasks) run once on the final incumbent and on `H_0` by `rrsi.py heldout --label champ`; OOD benchmarks are run by wrapper scripts on the final commit (`domains/workspace/ood/*.sh`, `domains/eng/scripts/final_eval.sh`, `domains/coding/scripts/swe_eval.sh`). No pre-registered plan, no confidence intervals, no repeats stated.

## (4) Tasks the proposer never saw

Inside the loop, **no**: the evolve set is simultaneously the feedback source (the proposer can `read_trace` any evolve task, with the verifier verdict "always included") and the selection set. The paper frames this as adaptive data analysis (Dwork et al. 2015) and treats δ and the critic as the mitigation (§3.2–3.3). Leakage controls are therefore **content screens, not information separation**: (i) a regex denylist that includes every Terminal-Bench task name, Harvey task/world ids, verifier paths, judge references, EngDesign task-id patterns, toolchain names and network/pip calls (`critic_patterns` in each adapter); (ii) an Opus critic reading the diff (120k-char cap) with six reject classes: leakage, degenerate, grader gaming, undeclared bundling, runtime memory/skill leakage, unbounded work (https://github.com/google-research/rrsi/blob/main/rrsi/critic.py); (iii) a `_LEAKY` regex on memory writes in `mechanisms.py`; (iv) the eng gateway's path containment plus `bwrap` jail with no network so the agent cannot grep for `solution.txt`. Only the Harvey 40-task held-out, SWE-bench Verified, JobBench, GDPval, APEX-Agents, EngDesign v1 (same tasks with "nine grading exploits closed") and Frontier-Eng are unseen, and they are measured once at the end.

## (5) Is the improver improved?

**No.** Proposer, analyst, digester and critic are fixed Opus 4.8 with fixed prompts (`RRSIConfig.proposer_model/analyst_model/critic_model`; constitutions are static files). The "recursive" in RRSI means only that the next round's trajectories come from the harness the previous round changed ("feedback from the current system is used to improve the harness that shapes its subsequent behavior", paper §1). The closest thing to improver adaptation is **in-context**: the proposer is conditioned on the edit history `L_t`, the prune set, and its own prediction hit/miss scoreboard ("over-claiming counts against you") — no validated update to the improver, no R0-vs-R1 comparison. Policy-robustness tests (Table 3/4) validate the *harness* across backbones, not the improver.

## (7) Failure modes they report, and ones others found

- Paper: three overfitting routes — benchmark-specific fitting, noise chasing, complexity accumulation (§1); prior methods "retain little of their evolve-set gain and several end below H0" (Fig. 1). Case study (Table 6): R0-B rejected by cost rule (+1.69 pts, +26.1% tokens); R8-B rejected by floor (−2.81 pts despite −13.6% tokens); eng R2 accepted a "bounded recovery hint for the recurring 'workdir must be an existing directory' tool-use error" (122→128/244, +1.6% tokens).
- Priors baked into the constitutions from measured experience: textual reference skills "tend to wash out" (~20 of them → zero-to-negative); subagent self-review "tends to be rejected on cost"; an always-on semantic pre-finalize gate "adds a third or more tokens per trial, rarely raises the pass count, and can multiply the invalid rate" (https://github.com/google-research/rrsi/blob/main/domains/eng/PATTERNS.md); verifier gaming "is not hypothetical" (eng SKILL.md). Engineering defenses in code: proposers that declare edits but change zero files are bounced; declared component tags are re-tagged from the diff because a proposer can relabel a prompt tweak as a `skill` to satisfy a reserved slot (`components.has_evidence`); harbor cannot resume jobs; Docker network exhaustion.
- External: issue #2 (2026-09-25) — Table 2 ablation arms are not in the release and `b_min` is never reached; maintainer acknowledged both, promised a fix and the number of runs per row; nothing landed since (PRs #3/#4 open) (https://github.com/google-research/rrsi/issues/2, https://github.com/google-research/rrsi/pull/3, https://github.com/google-research/rrsi/pull/4). Tyler-R-Kendrick's reimplementation reports seeded null runs where the paper's workspace acceptance rule "accepts noise in 33/40 runs" and the coding rule in 10/40 (summarizer-derived; **unverified**) (https://github.com/Tyler-R-Kendrick/harness/pull/28). grigio.org (2026-10-02): gains modest, evolved harness costs 2.42M vs H0's 1.56M tokens, smallest evolve gains of any method. My own check: with single runs, SWE-bench +1.8 on 500 (binomial SE ≈ 1.7 pts) and APEX +3.7 on 480 (SE ≈ 2.2 pts) are each ≈ 1–2 SE; the paper's generalization claim rests on direction across six splits, not on any interval.

## (9) Agent and harness design

**Agent loop (base harness, not RRSI itself).** Workspace/eng: archipelago `react_toolbelt` — a ReAct loop where each step first checks ReSum (summarize at 70% of the context window, keep last 10 messages verbatim, incremental running summary folded into a single user message), then one LLM call with meta-tools + current toolbelt + `final_answer`; tools are discovered dynamically (`toolbelt_list/inspect/add/remove_tool`, max 80), `todo_write` plans, and `final_answer` is **rejected while any todo is incomplete** (the only finish check); tool results are head/tail-truncated at 24k tokens (20k head / 5k tail chars; > 200k chars returns an error); MCP tool calls run under a 3,600 s timeout, fatal MCP errors end the run, other errors are fed back as text; empty LLM responses are re-prompted with "Continue"; limits `max_steps = 250`, `timeout = 10,800 s`, LLM timeout 600 s; no retry logic beyond that (https://github.com/google-research/rrsi/blob/main/third_party/archipelago/harness_workspace/main.py, …/resum.py, …/tool_result.py, …/README.md). Coding: Terminus-2 — the policy returns JSON `analysis/plan/commands`, each command is raw keystrokes into tmux with a wait duration; terminal output is capped at 10 KB head+tail (`_limit_output_length`); proactive summarization when free tokens < 8,000 and reactive unwind to 4,000 free tokens; completion requires `task_complete` **twice** (`_pending_completion`) (https://github.com/google-research/rrsi/blob/main/third_party/harbor_terminus2/terminus_2.py). Eng's `prompts.py` is "deliberately BARE at v0" — no doctrine, no mention of the verifier — so that any verification behavior must be discovered and paid for by the search (https://github.com/google-research/rrsi/blob/main/third_party/archipelago/harness_eng/prompts.py).

**Structural substrate.** `mechanisms.py` ships inert primitives the proposer may wire in: `Memory` (fcntl-locked JSONL, semantic/episodic, filtered reads, `_LEAKY` write guard), `ToolRegistry` (host-side callables, 4k-char results), `subcall` (one bounded extra policy call, returns "" on error), and for coding `upload_skills` (copies `skills/<name>/SKILL.md` into the container for progressive disclosure) (https://github.com/google-research/rrsi/blob/main/third_party/harbor_terminus2/mechanisms.py).

**How a change is represented, applied, versioned.** A candidate is a **git commit of the harness directory** on branch `<domain>/r<t><variant>` in its own worktree, drafted from `evolve/<domain>`; the diff is `git add -N` + `git diff` so new files are reviewed in full (`rrsi/gitops.py`). The proposer's `done()` must carry per-edit metadata: `id, component, hypothesis, targets_mode, why_not_lower_lever, trigger_condition, predicted_affected (concrete task ids), retroactive_check (corrective/preservative/transfer), regression_risk`. Acceptance fast-forwards `evolve/<domain>`; `frontier.json` records the harness **tree hash** so commits outside the harness never look like a change; `history.jsonl` holds one record per edit with ΔS, ΔC, outcome ∈ {ACCEPTED, REJECTED, LOST, critic_reject, smoke_fail, eval_invalid, no_proposal}. Rollback: no automatic rollback; `readjudicate --t` re-runs Alg. 2 on stored measurements (after removing later rounds) and `update-ref`s the branch; `reevaluate --t` re-measures a round after infrastructure failure (https://github.com/google-research/rrsi/blob/main/rrsi/loop.py).

**Isolation and testing before use.** Order per candidate: critic (regex precheck → Opus review) with up to `repair_rounds = 5` repair passes where the proposer sees only the objections; component tags re-derived from the diff; commit; **smoke** = `compileall` + a constructor/entry-point import check in the runner's Python + a real run on 2 (coding), 4 (eng, chosen among tasks the incumbent passes on every trial) or the split's smoke ids (workspace), 1 trial each, requiring no missing trials, and for eng no empty payload and mean score > 0; then the full evaluation. The sandbox protects the **benchmark**, not the host: eng `code_exec` runs under `bwrap` (read-only system, workspace the only writable mount, `--unshare-all`); coding tasks run in harbor's Docker containers but "the scaffold runs on the HOST (not in the container)"; the proposer-written Python executes unsandboxed in the runner process in all three domains. Drafting is path-jailed (`Workspace._safe`), but that is a write jail, not a runtime sandbox.

## (10) Self-improvement design

**Signal.** From the incumbent's own evaluation, `build_traces` takes the **worst trial of the `n_fail_traces` lowest-scoring tasks (30/60/22) plus the best trial of the `n_success_traces = 6` highest** (success habits the proposer must not break). A batch **analyst** (Opus, ≤ 30 turns) never reads traces; it dispatches read-only **digesters** (Opus, ≤ 15 turns, allow-listed read-only shell, 6,000-char output cap) over rendered traces, one task each, through three lenses — `failure` (blocker, narrative, verifier evidence, needed_instead), `capability_gap` (wanted / why_couldnt), `success` (habits, risk_if_removed) — and aggregates a **three-lens report**: failure modes ranked by impact with stable names across rounds (`global_analysis.json`), capability gaps, success habits; it must not prescribe code or attribute blame "model vs scaffold" (https://github.com/google-research/rrsi/blob/main/rrsi/analyst.py, https://github.com/google-research/rrsi/blob/main/rrsi/digester.py). Rendered traces end with the ground-truth verifier/rubric block, so **the proposer sees per-criterion verdicts and judge rationales of evolve tasks** (https://github.com/google-research/rrsi/blob/main/domains/workspace/render.py).

**Diagnosis granularity.** Per task (digests) → aggregate (report) → the proposer may drill back into raw traces by step range. The proposer context, in order: variant brief, edit history `L_t` (last 40 records, ≤ 4 unmeasured), attribution scoreboard (last 20), exploration directives `E_t`, prune set `B_t` with the accepted machinery to remove, the report, per-task digests, the **entire harness source**, `b_t`, task; constitution + `PATTERNS.md` are sent as a cached prefix.

**Avoiding refuted ideas.** (a) `L_t` with the instruction "A rejected mechanism is negative evidence; do not redraw it unchanged"; (b) `PATTERNS.md` as a curated memory of measured priors, including the nuance that "a mechanism that is refuted at one cost is not thereby refuted at another"; (c) stall detection `σ_t = 1[S_t − S_{t−w} ≤ δ]`, `w = 3`, reserving a slot for components in `U_t = K \ T_t`; (d) prune targets `B_t = {ℓ : g_t(ℓ) ≤ 0}` over `n_prune = 4/4/5` rounds (advisory: removal is itself an edit that must pass selection); (e) novelty `ν` for never-accepted structural types, counted only within the noise band; (f) the scoreboard penalizing over-claimed `predicted_affected`. There is no novelty metric over diffs and no archive of losing candidates beyond the history records.

**Stopping.** None beyond `T`; stall triggers exploration, not termination; the floor against `S*` prevents drift but never ends the run.

## What ouroloop can take from this

- **Borrow (cheap, fits M4/M3 as-is):** (i) the per-edit proposal schema — `component` tag validated against the diff, `trigger_condition`, `predicted_affected` task ids, and the three-part retroactive check — plus the **attribution scoreboard** that feeds prediction hit/miss back to R; v0.2's R1 ("say what each rejection rules out, prefer narrow triggers") converged on the same idea by itself (RESULTS.md). (ii) A **cost rule** that makes tokens/attempt a first-class acceptance criterion (`ΔC ≤ β0 + β1·ΔS`): W* in v0.2 rose from $0.452 to $0.570 per attempt with nothing in the gate to see it. (iii) The **analyst/digester split**: read-only, hard-capped per-trace digests with a `success` lens so the proposer is told which passing behaviours it must not break; ouroloop's per-task notes are the digest half without the success lens. (iv) The **constitution + pattern library** as versioned, measured priors ("textual skills wash out", "refuted at one cost is not refuted at another") — exactly the material ouroloop's research slot should be allowed to edit.
- **Ouroloop already does better:** a **sealed, pre-committed held-out final with bootstrap intervals** (RRSI measures held-out once, post hoc, no intervals, no seeds, and SWE-bench +1.8 / APEX +3.7 are ≈ 1–2 SE on single runs); **train/dev/final information separation** (RRSI's proposer reads the verifier verdicts of the very tasks that select the winner, and relies on a hand-fixed δ to absorb the adaptivity); a **budget ledger with reservations** and full cost reporting ($153 and $373 per activity) where RRSI reports no search cost at all; **R recursion with an R0/R1 comparison**, which RRSI does not attempt; **Docker-isolated package code** where RRSI runs proposer-written Python on the host; and a **per-task regression rate in the gate**, which RRSI only shows to the proposer.
- **Trap 1 — RRSI's acceptance is a hill-climb against a fixed δ on the selection set.** The floor is `S* − δ`, so a candidate may be accepted while scoring below the incumbent if it saves tokens or adds a never-tried structural component (coding: ΔC < −0 or ν = 1 with < 3.3% token growth suffices); with `m = 2` and `k = 2` this is one comparison of two noisy numbers per round, and an independent reimplementation reports the paper's workspace rule accepting noise in 33/40 null runs (unverified). Do not import the noise-floor rule in place of ouroloop's paired gate; at most use it as an extra filter.
- **Trap 2 — "you must ship a candidate", every round, two full evaluations.** RRSI spends 2 × |evolve| × k trials per round regardless of evidence quality (≈ 9.8k trials for the workspace run by my count) and has no stop rule; ouroloop's "at most one candidate with abandon conditions" and its budget root are the right shape for a 25-task dev set — the lesson from RRSI is to make the *proposer* evidence-disciplined, not to force proposals.
- **Trap 3 — leakage control by regex + LLM critic is not information separation.** RRSI needs a denylist of every task name, every verifier path, and a memory-write regex because the proposer can see everything; the eng SKILL.md admits verifier gaming "is not hypothetical" and EngDesign v1 exists to catch it. Ouroloop's split discipline makes most of that machinery unnecessary; adopt the critic only as a cheap pre-evaluation screen for the few leaks the split cannot stop (task facts carried from train notes into package text), never as the reason to let R see dev/final.
